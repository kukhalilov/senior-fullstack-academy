
# properties indexers fields methods parameters and overloads — Big-picture orientation and mental model

# Problem and purpose
In C#, types (classes, structs, records) are the blueprints for your data. However, a blueprint is useless if it cannot store information or perform actions. Members are the building blocks that define what a type *is* (state) and what it *does* (behavior).

The challenge for developers is choosing the right member type to balance safety, readability, and performance. Should you expose a raw variable, or wrap it in logic? Should you allow array-like access, or force a method call? This lesson explains how to use these members to build robust, predictable APIs.

# Plain-language mental model
Think of a C# type as a small API with internal storage and public operations:

*   **Fields** are storage locations owned by an instance or by a type.
*   **Properties** expose accessors and may store, validate, compute, or delegate values. They are not fields and do not promise security.
*   **Methods** expose callable behavior and may be instance or static, synchronous or asynchronous, stateful or pure.
*   **Indexers** expose keyed access through `[]`; keys can be strings or other types and need not be numeric.
*   **Parameters** define how arguments are mapped and passed at a call site.

# How the parts fit together
Members are organized by their role in the type's contract:

1.  **State Management:** Fields provide storage. Properties provide accessor-based contracts that may or may not use storage.
2.  **Behavior:** Methods execute logic.
3.  **Access Patterns:** Indexers provide keyed access (like `cache["user-42"]` or `matrix[row, column]`).
4.  **Binding:** Parameters define how data flows into methods, and overload resolution determines which specific method runs when you call it.
5.  **Modifiers:** Keywords like `static`, `virtual`, `override`, and `partial` control how these members behave across inheritance or when generated by tools.

# Concept map
*   **Fields:** Store state directly.
*   **Properties:** Expose controlled read/write behavior (get/set/init).
*   **Methods:** Represent actions; selected via overload resolution.
*   **Indexers:** Provide array-like access to an object.
*   **Parameters:** Define how values cross the boundary into a method (ref, in, out, params).
*   **Extension Members:** Add functionality to existing types without modifying their source code.

# End-to-end walkthrough
Imagine a `ShoppingCart` class:

1.  **Field:** You use a private `List<Item> _items` field to store the data internally.
2.  **Property:** You expose a `Count` property. It doesn't just return a variable; it returns `_items.Count`. This is a **computed property**.
3.  **Method:** You add an `AddItem(Item item)` method. This method validates that the item is in stock before adding it to the list.
4.  **Indexer:** You add an indexer so the user can write `cart[0]` to get the first item, making the API feel natural.
5.  **Parameters:** A separate `AddItems(params Item[] items)` method could accept `cart.AddItems(item1, item2, item3)`; use `params` only when that call shape improves the API.

When you call `cart.AddItem(myBook)`, the compiler looks at the method signature, checks the arguments, and uses **overload resolution** to ensure the correct version of `AddItem` is executed.

# When to use it and tradeoffs
*   **Use Fields** for storage when direct member access fits the contract, especially for implementation state. Public fields are legal and can suit simple data carriers, but expose assignment directly and offer no accessor hook or property-shaped abstraction.
*   **Use Properties** when the API models values callers read or assign; accessors can validate, compute, notify, or delegate, but should remain unsurprising and are not security boundaries.
*   **Use Methods** for named operations; parameter count, cost, mutation, or duration alone does not decide API shape.
*   **Use Indexers** when keyed lookup is natural to the abstraction, including maps and multidimensional data. A collection is common but not the only possible use.
*   **Tradeoff:** Over-using `ref` or `out` parameters can make code harder to read and debug. Stick to simple value passing unless performance requirements (like avoiding large struct copies) demand otherwise.
