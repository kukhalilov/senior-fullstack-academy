# How this group fits the mental model

To understand how a human-written source file becomes an executing software process, you must separate **compile-time tools** from **runtime components**, and **language specifications** from **execution environments**.

Imagine a construction project:
1. **The Blueprint (Programming language & C# compiler):** You write source code in a programming language. The compiler checks your syntax and translates human-readable text into a portable bytecode called Intermediate Language (IL).
2. **The Tools (SDK, CLI, MSBuild, NuGet):** The Software Development Kit (SDK) contains all the build tools needed to compile code, manage dependencies via package managers, and package applications for deployment.
3. **The Engine (CLR & Runtime):** When you run the application, the Common Language Runtime (CLR) takes the IL code, translates it to native machine instructions, manages memory, and executes it.
4. **The Raw Materials (BCL & Shared Frameworks):** Reusable libraries provide fundamental data types, file I/O, networking, and web primitives so you do not have to write them from scratch.

This modular boundary is what separates developers writing code (who need the SDK and compilers) from servers running applications (which often need only the lightweight runtime).

# Supplied names explained

Every item in the reference inventory plays a strict, bounded role in the source-to-running-process chain.

### Core Architecture and Execution

* **.NET platform:** The overarching collection of languages, compilers, runtimes, libraries, and tooling maintained by Microsoft for building and running applications across operating systems.
* **Programming language:** A human-readable formal language (such as C#) used to express algorithms and data structures before compilation.
* **C# compiler:** The tool that parses your source files and translates them into Intermediate Language (IL).
* **Intermediate Language (IL):** A portable instruction format generated by the compiler. A JIT-based runtime compiles methods to native machine code during execution; ReadyToRun and Native AOT can produce native code earlier.
* **Common Language Runtime (CLR):** The execution engine for .NET applications that provides services such as memory management (garbage collection), type safety, exception handling, and JIT (Just-In-Time) compilation.
* **.NET runtime:** The collective installation package containing the CLR and core libraries required to execute compiled .NET applications.
* **Base Class Library (BCL):** A foundational set of class libraries defining primitive types, collections, mathematics, and basic input/output operations.
* **.NET runtime libraries:** Extended libraries supplied alongside the CLR that provide platform primitives, cryptography, and threading utilities.

### Tooling and Build Chain

* **.NET SDK:** The development toolset containing the CLI, MSBuild, compilers, and targeting/build assets. SDK installations also include runtime components, but SDK selection and the runtime an app targets or uses are separate decisions.
* **.NET CLI:** The command-line interface (`dotnet`) used to initialize, build, run, and publish applications.
* **MSBuild:** The underlying Microsoft Build Engine that processes project files, resolves dependencies, and orchestrates compilation tasks.
* **NuGet package manager:** The mechanism used to download, install, and resolve third-party library dependencies.
* **Application framework:** A higher-level collection of libraries providing specialized architectural patterns (such as web APIs or desktop windows).
* **ASP.NET Core shared framework:** A built-in framework module for building modern web applications, APIs, and microservices.
* **Microsoft.NETCore.App shared framework:** The base shared framework containing the core runtime libraries needed by modern console and desktop applications.

### CLI Inspection Commands

* **dotnet executable:** The primary host binary (`dotnet`) that drives both CLI commands and .NET application execution.
* **dotnet --info:** A diagnostic command that prints detailed information about the installed SDKs, runtimes, environment variables, and OS architecture.
* **dotnet --version:** A command that outputs the selected SDK version for the current CLI invocation; `global.json`, working directory, and SDK resolution rules can affect which version is selected.
* **dotnet --list-sdks:** A command that displays all .NET SDK versions currently installed on the local machine.
* **dotnet --list-runtimes:** A command that displays all .NET execution runtimes currently installed on the local machine.

### Project Structure and Lifecycle Phases

* **SDK-style project:** A clean, concise XML project format used by modern .NET that automatically imports default targets and compilation properties.
* **Solution file:** A container file (`.sln`) that groups multiple related SDK-style projects together.
* **Project file (.csproj):** An XML file describing a single project's target framework, package references, and build settings.
* **Restore:** The phase where NuGet resolves dependencies and obtains required package assets, normally using local caches and configured feeds.
* **Build:** The phase where MSBuild evaluates the project and invokes compilation tasks to produce build outputs; `dotnet build` normally performs restore unless disabled or already handled.
* **Run:** The phase where the `dotnet` host launches the compiled assembly inside the runtime.
* **Publish:** The phase where the build system bundles the application and all its dependencies into a deployment-ready directory.

### Conceptual Distinctions

* **Compile-time versus runtime:** Compile-time refers to actions occurring when code is built by the SDK; runtime refers to actions occurring when the application executes inside the runtime engine.
* **Build-time tools versus runtime components:** Build-time tools (like MSBuild and compilers) are used by developers to create binaries; runtime components (like the CLR) execute those binaries on target machines.
* **Language version versus target framework:** Language version dictates which C# syntax features you can write (e.g., records or pattern matching); the target framework dictates which API contracts are available at compile and link time.
* **SDK version versus runtime version:** The SDK version represents the toolset installed on your machine; the runtime version represents the execution engine environment executing the code.
* **Installed runtime versus target framework:** The target framework is the API contract declared in your project file (`.csproj`), while the installed runtime is the physical engine present on the machine executing the application.
* **Reference assembly versus implementation assembly:** A reference assembly contains only the metadata and signatures needed to compile code against an API, whereas an implementation assembly contains the actual executable logic.

# Cross-item comparison

Understanding the boundaries of .NET requires distinguishing tightly coupled conceptual pairs:

* **.NET SDK vs. .NET Runtime:** The SDK supplies development tools and build assets; a runtime supplies components used to execute applications. A server running framework-dependent apps needs a compatible runtime, while self-contained apps carry runtime components. Some server workflows may also require SDK tooling.
* **Language Version vs. Target Framework:** You can target a modern framework (like .NET 10) while opting into older C# language versions, or use modern C# language features while targeting older frameworks, provided the compiler supports the combination.
* **Restore vs. Build vs. Publish:** *Restore* fetches external packages; *Build* compiles your local code into assemblies; *Publish* bundles your application, configuration, and dependencies into a self-contained or framework-dependent deployment package.

# Examples

### Example 1: Inspecting Environment Tooling
Before compiling code, developers use CLI commands to verify their environment:

```bash
# Display general environment, OS, and installed SDK/runtime paths
dotnet --info

# List all local SDK versions to ensure compatibility
dotnet --list-sdks

# List all available execution runtimes
dotnet --list-runtimes
```
*Expected result:* `dotnet --info` reports detailed .NET installation and machine environment information, including OS and version identifiers. `dotnet --version` reports the selected SDK version; `--list-sdks` and `--list-runtimes` list installed versions for the invoked architecture.

### Example 2: Compiling and Running an SDK-Style Project
An end-to-end command sequence executed via the `dotnet` executable:

```bash
# 1. Fetch missing NuGet package dependencies referenced in the .csproj
dotnet restore

# 2. Compile source code files into Intermediate Language (IL) assemblies via MSBuild
dotnet build

# 3. Execute the compiled application inside the Common Language Runtime
dotnet run
```
*Expected result:* Restore resolves required package assets, build produces project outputs if prerequisites are present, and run builds/restores as needed before executing the application's entry point. Exact output depends on the project and environment.

# Common mistakes

* **Confusing the SDK with the Runtime:** Installing only the runtime on a developer workstation prevents you from compiling code because compilers and MSBuild are part of the SDK.
* **Mismatching Target Framework and Installed Runtime:** A framework-dependent app needs an installed runtime compatible with its target framework and runtime configuration; self-contained apps include runtime components but still require compatible OS/architecture and dependencies.
* **Assuming Language Features Equal Framework Features:** Using a new C# language keyword requires a compatible C# compiler version, but calling a new BCL class requires a compatible target framework (`TargetFramework`).

# Knowledge checks with answers

1. **Question:** What is the primary difference between the .NET SDK and the .NET runtime?
   * **Answer:** The .NET SDK contains development tools; a runtime supplies execution components. SDK installations include runtime components, but installed SDKs and runtimes are listed and selected separately.

2. **Question:** Which command should you run to inspect which SDK versions are currently installed on your workstation?
   * **Answer:** `dotnet --list-sdks`.

3. **Question:** During which build phase does NuGet fetch missing third-party packages?
   * **Answer:** The *Restore* phase.

4. **Question:** True or False: Intermediate Language (IL) is executed directly by the physical CPU hardware without a runtime engine.
   * **Answer:** False. IL is a CPU-independent instruction set that must be processed and compiled into native machine code by the Common Language Runtime (CLR).
