# React API reference React hooks components context and resources — Reference: React Server Component directives

## Scope and version

This reference explains the two supplied directives, `'use client'` and `'use server'`. They are string directives recognized by React-compatible frameworks and bundlers; they are not ordinary runtime functions and do not independently create a complete server/client architecture. Availability and behavior depend on an RSC-capable framework or bundler. [React directives](https://react.dev/reference/rsc/directives) [React versions](https://react.dev/versions)

## How this group fits the mental model

`'use client'` marks a module-graph boundary: that module and its transitive imports become client code. It enables state, event handlers, Effects, and browser APIs in the marked subtree, but does not mean every rendered child must originate from a client module. `'use server'` marks a Server Function reference that client code can invoke through framework transport. One directive selects a client module boundary; the other marks an asynchronous callable server operation. Neither is an authorization system.

## Supplied names explained

- `'use client'` must appear at the top of a module, before imports/statements, to mark that module as a Client Component entry point. Client components may use state, Effects, event handlers, and browser APIs. Every imported dependency in the module subtree is included in client code. Props crossing from a Server Component to a Client Component must satisfy the framework/React serialization boundary. Mark only necessary entry points; imported child modules inherit client execution without needing repeated directives. [use-client](https://react.dev/reference/rsc/use-client)
- `'use server'` marks an async Server Function, either at module top level to mark exported functions or inside an async function body. A reference can be serialized to client code and invoked remotely by a compatible framework. Arguments are untrusted request data: validate shape and business rules, derive identity from trusted authentication, authorize each operation/resource, rate-limit where appropriate, and make mutations robust to duplicate or concurrent invocation. Do not expose secrets through returned values or errors. It does not mark a Server Component; React has no `'use server'` Server Component directive. [use-server](https://react.dev/reference/rsc/use-server)

## Cross-item comparison

`'use client'` changes how a module and its imports participate in the client bundle. `'use server'` exposes an asynchronous server operation through a generated reference. They can occur in the same application but serve opposite boundary roles. Neither should be mistaken for an authorization check, a request validator, or a substitute for framework configuration. [React directives](https://react.dev/reference/rsc/directives) [use-client](https://react.dev/reference/rsc/use-client) [use-server](https://react.dev/reference/rsc/use-server)

## Examples

```jsx
'use client';

import { useState } from 'react';

export function SaveButton({ initialSaved }) {
  const [saved, setSaved] = useState(initialSaved);
  return <button onClick={() => setSaved(value => !value)}>
    {saved ? 'Saved' : 'Save'}
  </button>;
}
```

This file is a Client Component entry. The `initialSaved` value crosses the framework boundary and must use a supported serializable value. The client-side toggle is only presentation; a real saved state must be persisted and authorized by the server.

```js
'use server';

export async function renameProject(projectId, proposedName) {
  const user = await requireAuthenticatedUser();
  const id = validateProjectId(projectId);
  const name = validateProjectName(proposedName);
  await requireProjectPermission(user.id, id, 'rename');
  return updateProjectName(id, name);
}
```

This illustrates the security shape, but helper names are application-specific and not React APIs. Framework deployment must provide the Server Function transport. Validation and authorization are deliberately inside the server function.

## Common mistakes

- Assuming `'use client'` affects only one component while its imported module graph still contains server-only dependencies.
- Adding `'use client'` to every file rather than choosing client entry boundaries.
- Assuming a Server Component passed as JSX children to a Client Component becomes client-executed source.
- Using `'use server'` to mark a Server Component.
- Treating a Server Function reference as private or trusted merely because it is generated by a framework.
- Returning database objects, secrets, or non-serializable values across the boundary without checking the supported protocol.
- Skipping validation and per-resource authorization inside remotely callable functions.

## Knowledge checks with answers

1. **Does `'use client'` include imported dependencies in the client module graph?** Yes, transitively.
2. **Does it make every JSX child source module a Client Component?** No; module graph and rendered tree are distinct.
3. **What does `'use server'` mark?** An async Server Function.
4. **Does `'use server'` itself authenticate a caller?** No; authentication, validation, and authorization are application responsibilities.
5. **What directive marks a Server Component?** None; React has no such directive.
