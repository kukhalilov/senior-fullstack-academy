## Scope and version

This lesson connects the nine supplied concepts across user identity, workload identity, perimeter availability, key custody, software integrity, and cryptographic migration. Protocol standards are cited at their current published editions as checked on 2026-11-20. Cloud-service capabilities and names are provider-specific; AWS pages here illustrate the distinction between WAF and managed DDoS controls, not a universal product taxonomy. Post-quantum migration is a program of inventory and staged replacement, not a claim that every system must immediately deploy a particular algorithm.

## How this group fits the mental model

Think of a request as crossing several trust boundaries. A person or application first proves an identity. A policy decision determines what that identity may do. The service then validates the particular credential presented for this request. Infrastructure must remain reachable under hostile traffic, keys must be controlled and recoverable under explicit policy, and software artifacts need verifiable build lineage. These are separate controls: a valid login does not authorize every action; encrypted data can still be accessed by an over-permissioned service; a signed artifact can still contain vulnerable code; and a WAF does not guarantee availability during a large volumetric attack.

Start from assets, callers, and threats. For each boundary, decide who issues an identity or credential, who validates it, what it is allowed to prove, how it expires or is revoked, and what happens if the issuer, network, or key service is unavailable. Prefer short-lived credentials and narrow permissions where operationally feasible, but plan their renewal, clock tolerance, outage behavior, and emergency revocation. Add protection at the layer where the threat acts rather than expecting one perimeter product to cover the whole path.

## Supplied names explained

### Human and delegated identity

- **OAuth 2.0** is an authorization framework for obtaining delegated access to a protected resource. It describes roles and token flows; it does not, by itself, define a user-login protocol. For an interactive user, the usual browser pattern is Authorization Code with PKCE. Register exact redirect URIs, validate state and issuer/mix-up protections as applicable, keep access tokens out of URLs, and treat refresh tokens as sensitive credentials. RFC 9700 deprecates the Resource Owner Password Credentials grant and the Implicit grant for new secure deployments. PKCE protects the authorization-code exchange; it is not client authentication and does not replace a confidential client’s authentication method. OAuth tokens may be opaque or structured, and a resource server must validate them according to the issuer and token profile rather than infer trust from their appearance.
- **OpenID Connect (OIDC)** layers authentication and standardized identity claims on OAuth 2.0. Its ID Token is intended for the relying-party client; it is not automatically an API access token. A client validates the signature using trusted issuer metadata/keys and checks issuer, audience, expiry, and the request nonce when used. Use the ID Token to establish the authenticated subject in the client’s context; use an access token, with the API’s expected audience and scopes/permissions, to call an API. Do not treat an arbitrary OAuth access token as proof of end-user authentication.
- **JSON Web Token (JWT)** is a compact claims format, not an authentication protocol and not necessarily encrypted. A signed JWT (JWS) provides integrity/authenticity under the chosen key; a JWE provides encryption to intended recipients. Base64url-decoding a JWT reveals data but verifies nothing. Pin an allowed algorithm set in application configuration, bind trusted keys to the expected issuer, validate issuer and audience plus the profile’s required claims, enforce expiry/not-before policy with bounded clock skew, and distinguish token kinds with mutually exclusive validation rules. Do not follow attacker-selected key URLs or accept `alg: none` as a shortcut. Opaque, reference tokens can be preferable when central revocation or minimal client-visible claims matter; JWTs can support local validation but key rotation, revocation latency, and claim staleness remain design concerns.

### Workload identity

- **SPIFFE/SPIRE** separates a portable workload-identity standard from a system that provisions it. A SPIFFE ID names a workload in a trust domain. An SVID is a verifiable document binding that identity to a cryptographic key; common profiles include X.509-SVID for TLS and JWT-SVID for token-based use. The SPIFFE Workload API lets a local workload retrieve SVIDs and trust bundles; SPIRE is one implementation that attests infrastructure and workload properties before issuing identities. This can replace manually distributed, long-lived service certificates with automatically renewed credentials, but it requires secure node/agent deployment, correct selectors and attestation, trust-bundle/federation management, and monitoring of renewal failures. An identity proves which workload is presenting a credential under the trust system; authorization still decides which operation it may perform. JWT-SVIDs also inherit bearer-token replay concerns unless protected by the surrounding protocol.

### Availability and key control

- **Distributed denial-of-service (DDoS) mitigation** reduces the chance that malicious volume or request patterns exhaust a service’s network, protocol, or application capacity. The defense is layered: upstream provider or scrubbing capacity for volumetric floods; edge caching and origin shielding for cacheable reads; network/transport filtering; per-route and per-identity rate limits; bounded request sizes and timeouts; admission control and load shedding; and a tested incident path with provider escalation. Make the expensive path hard to amplify: authenticate or cheaply validate before costly work where the product allows, cap fan-out, and protect dependencies. Rate limits must account for legitimate bursts, shared NATs, and attackers rotating identities. No architecture can promise that a finite service remains available under arbitrary attack volume; define protected journeys and degradation priorities.
- **Web application firewall (WAF)** evaluates application-layer web requests against managed or custom rules, such as request signatures, known exploit patterns, IP reputation, or rate-based rules. It is useful as one HTTP/S control, especially at an edge or gateway, but rules can create false positives and miss business-logic abuse. Keep application authorization, output encoding, input validation, secure defaults, and patching in place. A WAF is not a substitute for upstream network/transport DDoS capacity; the AWS comparison is one provider-specific illustration of the distinction.
- **Key management service (KMS)** provides controlled key operations and a policy/audit boundary for cryptographic key material. A common pattern is envelope encryption: a data-encryption key (DEK) encrypts application data, while a key-encryption key (KEK) held or controlled by KMS protects the DEK. Store ciphertext and wrapped DEK together with algorithm/version metadata; only authorized workloads can request unwrap/decrypt. Separate key administration from data access where possible, restrict principals and encryption context, audit use, and test backup/restore and key-disable recovery. Rotation does not necessarily re-encrypt every historical ciphertext, and deleting or disabling a key can make dependent data unrecoverable; key lifecycle is an availability and retention decision as well as a security decision.

### Artifact integrity and cryptographic transition

- **Supply-chain provenance** is verifiable evidence describing where, when, and how an artifact was built, including its builder and relevant inputs/dependencies. Provenance allows a consumer to compare a build against policy; it is not proof that source code is benign, that every dependency was captured, or that the builder itself is trustworthy. Verify the attestation’s signature and identity, artifact digest, expected builder, source revision, and policy constraints. Combine provenance with dependency controls, review, SBOMs, reproducible or isolated builds where appropriate, and vulnerability response. SLSA v1.2 defines a build-provenance predicate and increasing producer requirements; consumers still need verification policy.
- **Post-quantum cryptography migration** prepares systems to replace public-key mechanisms threatened by a sufficiently capable quantum computer. NIST’s FIPS 203 standardizes ML-KEM for key establishment; FIPS 204 standardizes ML-DSA signatures; FIPS 205 standardizes SLH-DSA signatures. A key-establishment mechanism and a digital signature solve different problems, so they are not interchangeable. Migration starts with an inventory of algorithms, certificates, protocols, libraries, vendors, and data retention; prioritizes data with long confidentiality lifetimes and hard-to-update embedded/partner systems; tests supported parameter sets, message/certificate sizes, performance, interoperability, and rollback; and establishes crypto-agile interfaces and key lifecycle procedures. A hybrid transition can be an interoperability strategy where standards and implementations support it, but it adds complexity and is not automatically stronger unless composition and downgrade handling are correct. Do not invent universal deadlines: follow current sector and jurisdiction guidance. “Harvest now, decrypt later” matters when recorded encrypted data may remain sensitive long enough for future cryptanalytic capability.

## Cross-item comparison

| Need | Appropriate concept | What it does not establish |
|---|---|---|
| Delegate an API permission | OAuth 2.0 access-token flow | That a human authenticated or that every API operation is allowed |
| Authenticate a user to a client | OIDC ID Token and validation | Authorization to call every resource server |
| Carry signed claims | JWT profile with strict validation | Confidentiality, freshness beyond its lifetime, or immediate revocation |
| Give a service a renewable identity | SPIFFE/SPIRE SVID and trust bundle | Business authorization or safe node attestation by itself |
| Preserve reachability under attack | Layered DDoS controls | Unlimited capacity or immunity to application-level abuse |
| Filter HTTP request patterns | WAF | Correct application logic or all network-layer flood protection |
| Protect data-encryption keys | KMS with envelope encryption | Correct data authorization, backup policy, or automatic recovery from key deletion |
| Check build lineage | Signed, policy-verified provenance | Harmless code or trustworthy builder unless independently established |
| Prepare public-key systems for quantum risk | Crypto inventory and staged PQC migration | A drop-in algorithm replacement without protocol and ecosystem changes |

The controls compose only through explicit policy. For example, an OIDC login can result in a narrowly scoped OAuth access token; an API can validate that token and then authorize a tenant-scoped operation; a workload SVID can authenticate the API-to-database channel; KMS policy can restrict which workload decrypts a DEK; edge DDoS controls can preserve the request path; and deployment admission can verify provenance before running the service. Each step needs its own failure and audit behavior.

## Examples

**A browser-based order application.** The user is redirected to an authorization server using Authorization Code with PKCE. The client validates OIDC’s ID Token for its issuer, audience, expiry, and nonce, then obtains an access token intended for the orders API. The API validates its token profile and applies authorization to the specific customer/order; merely having a valid JWT is insufficient. A backend service presents a short-lived workload identity to a downstream service. The order service encrypts sensitive fields with a DEK and asks KMS to unwrap that DEK only under a narrowly scoped principal and context. Its build pipeline emits provenance tied to the artifact digest, and deployment policy checks the expected builder/source before rollout.

**A traffic flood during a launch.** Put cacheable reads behind edge caching, retain sufficient upstream DDoS protection, define route-specific rate limits and admission budgets, and shed optional expensive features before the order-write path. Watch legitimate-success SLI and dependency saturation, not just raw request count. A WAF rule can block a recognizable HTTP pattern, but an attacker generating valid-looking requests may require application quotas, bot controls, or capacity policy. The incident plan should specify who can tune a rule and how false positives are reversed.

**An eventual PQC transition.** Inventory TLS termination, service-to-service certificates, signing, HSM/KMS support, customer integrations, archives, and update mechanisms. Rank by confidentiality lifetime and migration difficulty; test hybrid handshakes where the ecosystem supports them; measure wire-size and CPU effects; record algorithm identifiers and key versions; rehearse rollback without silently downgrading protections. Treat the migration as a multi-year compatibility and key-management program, guided by applicable current standards and policy.

## Common mistakes

- Calling OAuth a login protocol or using an ID Token as a general-purpose API credential.
- Treating a decoded JWT as validated, accepting whichever algorithm the token requests, or skipping issuer/audience/profile checks.
- Assuming PKCE authenticates a client secret or that a valid workload identity automatically grants application permissions.
- Believing a WAF alone absorbs volumetric floods, or that a DDoS provider can protect an origin that is directly reachable around the edge.
- Rotating a key without planning ciphertext compatibility, old-key retention, audit, and restoration; deleting a key before proving data lifecycle requirements.
- Treating an SBOM or provenance statement as a vulnerability-free guarantee; provenance is useful only when its signer, builder, subject digest, and policy are verified.
- Calling a KEM a signature algorithm, or claiming a post-quantum migration is done because one TLS endpoint supports a new cipher suite.
- Assuming stronger cryptography repairs weak identity issuance, overbroad authorization, compromised endpoints, or poor key custody.

## Knowledge checks with answers

1. **A user signs in through OIDC. Which token should the client use to call an API?** Normally an access token issued for that API; the ID Token’s audience is the relying-party client and its purpose is authentication.
2. **A JWT has a valid signature. Is it acceptable for this API?** Only if trusted key/issuer binding, token kind, audience, time bounds, and the application’s required claims and authorization checks also pass.
3. **What separates SPIFFE identity from authorization?** SVID validation establishes a workload identity under the trust domain; policy still maps that identity and request context to permitted actions.
4. **Why use both edge DDoS protection and a WAF?** They can address different traffic layers and patterns; neither replaces application-level quotas and safe behavior under overload.
5. **Does KMS rotation rewrite all stored ciphertext?** Not necessarily. The application must understand key versions and retain old key material as needed to decrypt existing data, following service semantics.
6. **What is the first useful PQC migration artifact?** A maintained cryptographic inventory linked to system owners, data lifetime, dependencies, and update constraints; it lets the organization prioritize and test migration rather than guess.
