# Kubernetes workloads configuration scheduling and networking — Core concepts and how they fit together

Sources: [Objects in Kubernetes](https://kubernetes.io/docs/concepts/overview/working-with-objects/), [Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/), [Controllers](https://kubernetes.io/docs/concepts/architecture/controller/), [Services](https://kubernetes.io/docs/concepts/services-networking/service/), [Resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/), [Scheduling](https://kubernetes.io/docs/concepts/scheduling-eviction/), [Kubernetes v1.37 release announcement](https://kubernetes.io/blog/2026/08/26/kubernetes-v1-37-release/), and [Gateway API](https://kubernetes.io/docs/concepts/services-networking/gateway/).

## Learning objectives

After this lesson, you should be able to trace a declarative change from client to running container; explain why accepted, scheduled, Running, Ready, and reachable are different states; choose an appropriate workload controller; distinguish stable service identity from ephemeral Pod identity; reason about resources, placement, data, security, and traffic together; and diagnose common symptoms by checking the layer that owns the behavior.

## Prerequisites

You should know what a process, container image, HTTP request, IP address, DNS name, CPU and memory are. A container is a process isolation/package mechanism, not a miniature virtual machine by definition. Kubernetes orchestrates containers through a cluster API; it does not turn a process into a reliable service without the application and surrounding integrations behaving correctly.

## Core concepts

A Kubernetes object is a typed record stored through the API. `apiVersion` and `kind` select the schema and type, `metadata` gives the object identity and relationships, `spec` describes desired state, and `status` reports observations. A namespace is part of the name for most namespaced objects. Labels support selection; annotations hold non-selector metadata. Owner references describe lifecycle relationships, while finalizers let a controller delay deletion until cleanup is complete.

The API server is the front door and authority for stored state. Clients authenticate, receive authorization decisions, and pass admission and schema checks. A successful write means an object was accepted, not that its asynchronous work completed. Controllers repeatedly compare observed state with desired state and take incremental actions. If a Deployment asks for four replicas but only three Pods are Ready, the controller keeps trying to make progress; it does not promise that a fourth replica is feasible.

Declarative apply is useful because a manifest describes a target that can be reviewed, diffed and reconciled. Server-side apply records field ownership in managed fields. A conflict means multiple managers claim incompatible ownership of a field and should be resolved deliberately; forcing ownership can erase another manager’s intent. Imperative commands remain useful for diagnosis and one-time actions, but they can make live state diverge from version-controlled manifests. `kubectl diff` previews a server-side comparison; it is not a transaction or guarantee that all dependent resources will become healthy.

Labels are exact matching data and selectors are evaluated against them. Equality selectors (`key=value`, `key!=value`) and set-based selectors (`in`, `notin`, `exists`, `doesNotExist`) are common. A Deployment’s selector must match its Pod template labels and is immutable in important ways; a Service with a selector that matches no Pod has no intended endpoints. Namespaces provide naming and policy scope, not a complete security boundary by themselves. ResourceQuota and LimitRange can constrain or default requests and object counts.

## Mechanisms and relationships

A Pod is the smallest schedulable unit. Its containers share a network namespace and Pod IP, can communicate over localhost, and can share declared volumes. Containers in one Pod therefore need coordinated placement and lifecycle; unrelated services usually belong in separate Pods. A Pod UID and IP are temporary implementation identities. When a controller replaces a Pod, it normally creates a new object with a new UID and potentially a new IP.

The kubelet and container runtime realize a Pod on its assigned node. Pod phase is deliberately coarse: `Running` does not mean each application is serving correctly. Conditions and container states provide more detail. Init containers run before regular application containers. A restartable init container with container-level `restartPolicy: Always` is the native sidecar pattern: it starts early, remains running alongside later containers, and has defined ordering/termination semantics. An ephemeral container can be added for debugging but is not an ordinary declarative application container and does not restart like a regular workload container.

Startup, liveness and readiness probes answer different questions. Startup protects slow-starting containers by holding off liveness/readiness evaluation until startup succeeds. Liveness asks whether restarting this process is the recovery action; an overly aggressive liveness probe can create a restart loop under load. Readiness asks whether the instance should receive traffic now. It is normal for a Pod to be Running but not Ready. `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds`, `successThreshold`, and `failureThreshold` determine probe timing and tolerance; use realistic timeouts and account for probe load. Exec, HTTP, TCP and gRPC actions test different contracts. A probe should not depend on a downstream service whose outage would cause every instance to restart.

Container commands and args interact with the image’s configured entrypoint and command. Environment variables, `envFrom`, ConfigMaps, Secrets and the Downward API inject configuration or selected Pod metadata. Environment-based values are snapshots at container start; projected files update according to volume behavior, but the application may still need to reread them. Never assume a Secret is encrypted merely because the API object is named Secret; storage encryption and access control are cluster responsibilities.

Termination is a cooperative sequence: Kubernetes asks the runtime to stop the container, the process normally receives SIGTERM, a `PreStop` hook may run, and the configured grace period bounds shutdown before SIGKILL. Exact timing details matter when hooks consume the grace period. Applications should stop accepting new work, finish or reject in-flight work within the deadline, and close resources. Pod disruption handling is distinct from process termination. `kubectl debug` and ephemeral debug containers help inspect a running workload without baking troubleshooting tools into the production image.

## 3. Controllers express different identity and completion semantics

A Deployment manages interchangeable replicas through ReplicaSets. It is the default choice for stateless request-serving applications. A rolling update creates new Pods while removing old ones according to `maxSurge` and `maxUnavailable`; incompatible readiness, capacity or selectors can stall it. `kubectl rollout status`, history and undo help observe and reverse a revision, but rollback does not reverse database schema changes or external side effects. A Recreate strategy terminates old Pods before bringing up new ones and trades availability for avoiding overlap.

A StatefulSet provides stable ordinal identities and stable storage association, usually paired with a headless Service for stable DNS. It is for software whose instances need predictable identity or ordered lifecycle, not a magic database backup or consensus protocol. `OrderedReady` waits for ordered readiness; `Parallel` relaxes Pod creation/deletion ordering. Rolling updates can use a partition to update only higher ordinals first. `OnDelete` waits for manual Pod deletion to apply template changes. StatefulSet semantics do not guarantee that an application can safely run with a particular replica count.

A DaemonSet targets eligible nodes, commonly for agents. A Job represents finite work and tracks completions, parallelism, retries, deadlines and successful termination; retries mean the job’s operation should be idempotent or otherwise safe to repeat. Indexed Jobs give each completion a stable index. CronJobs create Jobs on a schedule; time zones, missed schedules, concurrency policy, starting deadlines, history cleanup, controller downtime and duplicate/late work all matter. A schedule is not a guarantee of exactly-once execution. `Forbid` prevents overlap by skipping a schedule while a prior Job is active; `Replace` terminates the older Job; `Allow` permits overlap. Retained completed Jobs aid inspection but consume API storage.

ReplicationController is a legacy predecessor; ReplicaSet is normally managed by Deployment. Owner references and garbage collection determine what deleting a parent may remove. An orphan Pod has no higher-level controller expected to recreate it. The owner model supports orchestration; it does not establish application transaction boundaries.

## 4. Service identity decouples clients from changing Pods

A Service gives a changing set of backends a stable virtual address and DNS name. The selector identifies Pods; an EndpointSlice controller publishes eligible addresses, ports, conditions and topology. A kube-proxy implementation or an alternative data plane programs forwarding behavior. ClusterIP is the ordinary in-cluster service; NodePort exposes a port on nodes; LoadBalancer asks an implementation/provider to provision external reachability; ExternalName returns DNS indirection and does not proxy traffic. A headless Service disables a virtual IP and can expose per-Pod DNS. These are distinct reachability models, not security controls.

`port` is the Service-facing port; `targetPort` selects the backend port and can name a container port. CoreDNS typically resolves Service names. Pod DNS policy/configuration can alter resolver behavior. Debug name resolution, EndpointSlices, routing and application listening address separately: a Service can exist while having no endpoints, and a healthy endpoint can still be unreachable because of routes, policy or a process bound only to loopback.

Ingress provides HTTP(S) routing through a separately installed controller and is frozen for new feature development. Gateway API separates infrastructure ownership (`GatewayClass`), deployed listeners (`Gateway`), and application routing (`HTTPRoute`, `GRPCRoute` and protocol-specific routes). Route attachment is constrained by listener permissions, namespaces, parent references, hostname intersection and cross-namespace references such as `ReferenceGrant`. Standard and Experimental channels have different stability promises. `BackendTLSPolicy` configures backend TLS where supported. Neither API implements load balancing on its own.

NetworkPolicy is a declarative Layer 3/4 policy with pod/namespace selectors, ingress/egress directions and optional IP blocks. Policies select Pods and combine additively for allowed traffic; a policy allowing a flow in one direction does not automatically allow the return path as a separate new flow in all implementations. A CNI/network plugin must enforce it. Validate plugin capabilities and cluster defaults; “default deny” only follows when a selecting policy defines the relevant isolation direction.

## 5. Configuration and storage have different update and durability properties

ConfigMaps hold non-secret configuration and Secrets hold sensitive values by API convention. Neither should be treated as a complete secret-management solution. Environment variables are fixed at process creation. Mounted projections may update asynchronously, except for cases such as `subPath` mounts, but applications must watch/reload files safely. Secret values can appear in process environments, logs, backups or API access paths; use encryption at rest, narrowly scoped RBAC, rotation, and external secret systems where appropriate.

A volume is mounted into a Pod; storage semantics depend on the volume type and driver. `emptyDir` is tied to a Pod lifetime (and may be memory backed); `hostPath` couples the workload to node filesystem details and is security-sensitive. Projected volumes combine sources such as ConfigMaps, Secrets, service account tokens and downward API data. SubPath mounts expose a path within a volume and have special update behavior. A PV represents provisioned storage; a PVC is a workload request; a StorageClass describes provisioning behavior. Dynamic provisioning, reclaim policy, expansion and snapshots require driver capabilities and may have provider-specific constraints. Access modes describe attachment/access semantics and do not guarantee application-level file locking or simultaneous write safety.

Requests influence scheduling and resource accounting; limits constrain runtime consumption according to resource-specific behavior. CPU limits can throttle; memory excess commonly results in OOM termination. QoS class is derived from requests and limits, and affects eviction preference under pressure rather than guaranteeing availability. Ephemeral storage also consumes node capacity. An extended resource such as a GPU is not automatically available just because a manifest names it: a device plugin or Dynamic Resource Allocation integration must advertise and satisfy it.

In-place Pod resize became stable in v1.35. It updates CPU or memory requests/limits on a running Pod through `/resize`; `resizePolicy` controls whether a container must restart for the change. A request may be deferred if the node cannot provide capacity. This differs from changing a Deployment template, which starts replacement Pods through its rollout. VPA can recommend or apply resource changes depending on mode and version; avoid unmanaged competition between VPA, HPA and hand-edited values for the same control signal.

## 6. Scheduling and scaling are constrained control loops

The scheduler filters nodes that cannot run a Pod, scores feasible nodes, and binds the Pod. Requests, node allocatable resources, taints, selectors, affinity, topology spread, volume topology, priority and policy all influence feasibility. A `Pending` Pod is not necessarily a scheduler bug: inspect its events and the unschedulable condition. `nodeSelector` is a simple label constraint. Node affinity provides required or preferred expressions. Pod affinity attracts Pods near matching Pods; anti-affinity spreads them, but hard anti-affinity can make workloads impossible to place. Topology spread constraints use `topologyKey`, `maxSkew`, `minDomains` and `whenUnsatisfiable` to distribute replicas across zones or other domains.

Taints repel Pods unless they tolerate the taint; a toleration permits placement but does not attract a Pod. `NoSchedule` blocks new placement, `PreferNoSchedule` is a preference, and `NoExecute` can evict existing Pods unless tolerated. Priority can allow preemption of lower-priority Pods, but preemption does not fix a bad resource request or guarantee that a workload can make progress.

HPA changes a target’s replica count based on resource, custom, or external metrics. Resource metrics usually require resource requests and a functioning metrics pipeline. Scaling has sampling delay, stabilization windows and rate policies, so it is not instantaneous. In v1.37, scaling to zero for suitable object/external metrics is Beta and enabled by default; the workload’s trigger, cold start and request buffering must be designed accordingly. A Service does not queue HTTP requests while there are zero ready Pods. Cluster Autoscaler or another node autoscaler may add capacity when Pods cannot schedule, but cloud quotas, node group configuration and startup latency limit its effect. HPA changes Pod count; node autoscaling changes node capacity.

PodDisruptionBudget limits voluntary disruption through the eviction API, such as planned node drains; it does not prevent involuntary failures and does not override every administrative action. `minAvailable` and `maxUnavailable` express complementary budgets. `unhealthyPodEvictionPolicy` can help drain already unhealthy Pods. Misconfigured budgets can block maintenance, and a budget does not create replicas or capacity. Scheduling gates can hold a Pod from scheduling until another actor removes the gate. Node-pressure eviction is a separate kubelet response to local resource pressure.

Kubernetes v1.37 advances gang scheduling and workload-aware preemption to Beta through workload/PodGroup APIs. They address coupled groups that need coordinated placement, but availability and exact APIs depend on version and feature configuration; they are not interchangeable with ordinary per-Pod scheduling.

## 7. Security and extension are part of workload design

A ServiceAccount is a workload identity, and automatically mounted credentials should be disabled when unused. Bound projected tokens are short lived and audience scoped. Kubernetes authentication identifies a caller; authorization such as RBAC checks permitted verbs and resources; admission applies additional validation or mutation. These are distinct stages. A Role grants namespaced permissions and a ClusterRole can describe cluster-scoped or reusable permissions; RoleBinding and ClusterRoleBinding determine where those permissions apply. `kubectl auth can-i` tests authorization for a chosen identity and request, not network reachability or admission acceptance.

Pod Security Standards define Privileged, Baseline and Restricted policy levels. Pod Security Admission can enforce/audit/warn at namespace scope according to configured labels. A container securityContext controls user/group, privilege escalation, root filesystem, capabilities, seccomp and related settings. Host namespaces, privileged mode and broad host access increase blast radius. SELinux and AppArmor availability/configuration is node and runtime dependent. Apply least privilege and test the actual admission and runtime policy.

CustomResourceDefinitions extend the API schema; custom resources are instances. CRDs define scope, schema, defaults, pruning, served/storage versions and optional status/scale subresources. Conversion webhooks translate between versions when storage and served representations differ. An operator combines custom resources with a controller that reconciles domain-specific state. Mutating webhooks change incoming objects; validating webhooks accept/reject them. Their availability and `failurePolicy` can affect cluster-wide API writes, so design timeout, availability and rollout carefully. API feature stages and deprecation policy change over releases; inspect discovery, deprecation warnings, feature gates and server version rather than assuming every client supports a field.

## Worked examples

Start with a hypothesis at each boundary. `kubectl get deployment,replicaset,pod -o wide` shows whether the controller created Pods. `kubectl describe pod` and Events explain image pull, scheduling, mount or probe failures. `kubectl logs` and `kubectl logs --previous` distinguish current output from a terminated container. Check Pod conditions and readiness, then inspect the Service selector and EndpointSlices. Test DNS from an in-cluster client, then route/policy and the application’s listening address. Finally inspect Gateway/Ingress controller status if traffic enters from outside. Do not “fix” the problem by making the liveness probe weaker before confirming what it tests.

## Misconceptions and edge cases

- API acceptance is not successful scheduling, container startup, readiness, or user reachability.
- `Running` is a Pod phase, not an application health guarantee.
- A Service does not own or preserve Pod identity; it selects endpoints.
- Readiness controls endpoint eligibility; liveness can restart a container. Confusing them can amplify an outage.
- A toleration allows a Pod onto a tainted node but does not choose that node.
- Requests affect scheduling; limits and QoS affect runtime/eviction behavior. They are not interchangeable.
- PDBs help with voluntary eviction; they do not make a cluster highly available or stop node failure.
- Kubernetes Secret is an API type, not proof of encryption or safe access.
- NetworkPolicy, Gateway, Ingress, metrics, and storage objects require compatible implementations.
- A Job retry can repeat side effects. Exactly-once behavior must be designed at the application/data boundary.
- A successful rollout and rollback do not undo database or external system changes.
- Feature maturity upstream does not establish support in a managed distribution or older cluster.

## Knowledge checks with answers

1. **A Deployment applied successfully, but no Pod is serving. What does the success prove?** It proves the API accepted the Deployment update. Check controller-created ReplicaSets, scheduling, kubelet/container status, probes, Service endpoints and routing separately.
2. **Why use readiness and liveness separately?** Readiness removes an instance from traffic when it should not serve; liveness restarts a process when restarting is expected to recover it. A dependency outage should not usually make every Pod fail liveness.
3. **When choose StatefulSet over Deployment?** When instances need stable ordinal identity, stable storage association or ordered lifecycle. StatefulSet still requires an application-specific design for replication, failover and backup.
4. **What does a toleration mean?** The Pod is permitted to tolerate a matching taint. It does not imply attraction or guarantee scheduling there.
5. **What changes when an HPA scales a target to zero?** No Pods serve that target until a metric-driven scale-up completes. A suitable external/object metric, successful control loop, cold-start tolerance and any needed request buffering are required.
6. **How do you know whether a NetworkPolicy is enforced?** Confirm the cluster’s network plugin supports and enforces the relevant policy behavior; then test the actual path and both intended allowed and denied flows.
