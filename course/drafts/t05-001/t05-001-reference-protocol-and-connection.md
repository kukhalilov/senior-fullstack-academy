# HTTP HTTPS TLS certificates HSTS and transport security — Reference: HTTP over TLS, handshake, protocol negotiation, and replay boundaries

## Scope and version
This lesson explains the assigned protocol and connection names in the manifest. The current TLS 1.3 specification is [RFC 9846 (July 2026)](https://datatracker.ietf.org/doc/html/rfc9846), an IETF Standards Track Proposed Standard that obsoletes RFC 8446 while retaining TLS version 1.3. RFC 9849 standardizes Encrypted Client Hello (ECH). These current RFC editions supersede the earlier summaries below; exact implementation settings still depend on maintained platform guidance.

## How this group fits the mental model
Think in layers: HTTP defines what the client asks; HTTPS places that HTTP exchange inside TLS; the handshake establishes the protected channel and authenticates the server; browser identity checks decide whether the presented identity matches the requested service. Protocol negotiation can select how the application conversation proceeds. Early data creates a replay boundary that application code must respect.

## Supplied names explained
- `HTTP request and response` — A request identifies a method, target, fields, and possibly content; a response communicates a status, fields, and possibly content. HTTP semantics are shared across versions; see [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html).
- `HTTPS` — HTTP carried over a connection protected by TLS. It protects the browser-to-TLS-endpoint segment; it does not itself prove that the application is trustworthy.
- `TLS` — A protocol family for protecting client/server communications against eavesdropping, tampering, and message forgery, subject to correct configuration and secure endpoints. The IETF describes these aims in [RFC 9846](https://datatracker.ietf.org/doc/html/rfc9846).
- `TLS 1.2` — An earlier TLS version. RFC 9846 specifies new requirements affecting TLS 1.2 implementations as well as TLS 1.3; avoid treating legacy configuration advice as timeless.
- `TLS 1.3` — The newer version specified by RFC 9846. The protocol version remains 1.3; RFC 9846 supersedes the prior TLS 1.3 document RFC 8446.
- `RFC 9846 Proposed Standard status and replacement for RFC 8446` — RFC 9846 is Standards Track at the Proposed Standard maturity level, published July 2026. It formally obsoletes RFC 8446 and keeps the negotiated protocol version at TLS 1.3; “proposed” is a standards maturity label, not an unreviewed draft.
- `RFC 9846 TLS 1.3 technical updates` — The bis revision clarifies requirements and terminology and makes targeted protocol changes: do not reuse KeyShare values across connections; tighten PSK/HelloRetryRequest hash rules; require clients that do not support resumption to ignore NewSessionTicket; and strengthen key-update usage-limit requirements. It does not create a TLS 1.4 version.
- `TLS 1.0 and TLS 1.1 MUST NOT be negotiated` — RFC 9846 updates TLS 1.2 implementations to prohibit negotiation of TLS 1.0 and 1.1, consistent with RFC 8996; retain TLS 1.2 only where compatibility/policy requires it.
- `TLS 1.3 KeyShare values must not be reused across connections` — RFC 9846 explicitly prohibits reusing key shares between connections; implementations must generate fresh ephemeral key-share material as required by the protocol.
- `TLS 1.3 cipher suite versus key exchange and signature algorithms` — In TLS 1.3, cipher suites select record protection AEAD and hash; key exchange groups and certificate signature schemes are negotiated separately. Do not interpret a TLS 1.2 suite name as encoding the same choices.
- `TLS 1.3 HelloRetryRequest and key share` — The server may request a different key share when the client's offered groups do not allow a mutually usable share. The client sends a second ClientHello; the transcript and PSK binder rules are defined precisely by RFC 9846.
- `TLS 1.3 PSK resumption and binder` — A resumption PSK can avoid a full certificate-based handshake; the binder authenticates the ClientHello against the PSK-derived transcript context. PSK resumption does not automatically make early application data replay-safe.
- `TLS 1.3 NewSessionTicket` — The server can send tickets after the handshake for future PSK resumption. A client that does not support resumption must ignore them under RFC 9846; ticket handling and lifetime are implementation/deployment concerns.
- `TLS 1.3 post-handshake KeyUpdate` — Either endpoint can update traffic keys after handshake; RFC 9846 clarifies the mandatory key-usage limits and requires update before exceeding them. This is not a replacement for new-session policy.
- `TLS 1.3 encrypted handshake and server certificate` — After ServerHello, most handshake messages, including the certificate, are encrypted. The initial ClientHello still exposes some metadata unless an extension such as ECH is used.
- `TLS 1.3 handshake round trips and session resumption tradeoff` — A full TLS 1.3 handshake normally completes in one round trip; PSK resumption can reduce handshake work, and optional 0-RTT sends application data earlier but has replay risk. Faster setup changes security and replay assumptions rather than removing them.
- `TLS 1.3 downgrade protection` — The protocol uses downgrade sentinel values in ServerHello.random when a TLS 1.3 server negotiates TLS 1.2 or older, allowing TLS 1.3 clients to detect certain downgrade attacks. This does not repair weak legacy configurations or replace disabling obsolete versions.
- `TLS 1.3 0-RTT requires explicit application enablement` — TLS implementations must not enable sending or accepting early data unless the application specifically requests it; clients must not automatically resend rejected early data unless instructed by the application. Treat it as an explicit application/protocol feature.
- `TLS anti-replay state across server clusters` — TLS 1.3 requires a server instance not to accept the same early-data handshake repeatedly and recommends limiting replays further. Distributed deployments need shared/partitioned anti-replay state or must disable 0-RTT; TLS alone cannot prevent application-level duplicate requests.
- `Encrypted Client Hello ECH RFC 9849` — ECH encrypts the sensitive inner ClientHello, notably the true SNI and potentially ALPN, using a published ECH configuration. It aims to hide which server name within a cooperating anonymity set the client is contacting; it is not a complete traffic-anonymity system.
- `ECH ClientHelloOuter and ClientHelloInner` — ClientHelloOuter carries public routing/compatibility values and the encrypted ClientHelloInner carries the private parameters. The server accepts the inner hello or rejects ECH and may provide retry configurations; clients must validate ECH acceptance rather than silently assuming privacy.
- `ECH configuration and DNS publication` — A domain publishes ECH configuration, commonly through the `ech` SvcParam in HTTPS/SVCB DNS records under RFC 9848, or a client obtains it through another configured channel. Ordinary DNS publication does not itself provide cryptographic authenticity/provenance for the ECH config; DNSSEC and encrypted DNS have separate roles, and clients still authenticate the TLS service. Inconsistent/stale configuration can cause rejection and retry.
- `ECH public name and anonymity set` — The outer public name identifies a shared client-facing service; privacy depends on many destinations sharing externally indistinguishable behavior. A unique server/IP/configuration can make the anonymity set ineffective.
- `ECH rejection and retry configurations` — If the server cannot decrypt ECH, it completes a handshake using `ClientHelloOuter`; the client authenticates only the configured public name, not the origin, and MUST NOT report the connection successful to the application or send application data. It retries with authenticated `retry_configs` when provided; otherwise RFC 9849 permits a secure ECH disable/retry path. If it does not retry, it reports an error. Never treat the rejected outer-name handshake as an origin connection.
- `ECH limitations: DNS and IP address visibility` — ECH hides selected ClientHello fields but does not hide destination IP, plaintext DNS queries, packet timing/size, or the fact that the client uses a provider. Encrypted DNS and shared hosting can reduce some related leakage but do not make the channel anonymous.
- `ECH does not conceal all connection metadata` — Middleboxes can still observe IP addresses, timing, record sizes, connection duration, and unencrypted outer fields. ECH's protection is specifically about selected ClientHello contents within its threat model.
- `Encrypted DNS and ECH deployment relationship` — ECH configuration is commonly discovered through DNS HTTPS/SVCB records. Authenticated encryption between client and resolver can hide DNS queries from local network observers, but the resolver still sees the query and destination IP/traffic patterns remain visible. DNSSEC authenticates DNS data but does not encrypt it; these controls address different observers.
- `ECH SVCB downgrade and mandatory configuration` — Mixed HTTPS/SVCB endpoints where some advertise ECH and others do not can permit a network attacker to steer clients to a non-ECH endpoint. RFC 9848 warns against mixed configurations; use consistent ECH publication, appropriate mandatory parameters where supported, and client SVCB-reliant behavior to avoid silent downgrade.
- `TLS 1.3 0-RTT replay protections and HTTP method safety` — 0-RTT lacks inherent cross-connection replay protection. HTTP safe-method semantics do not guarantee an endpoint has no side effects; avoid early data for operations whose duplicate execution matters or implement end-to-end replay defenses.
- `TLS 1.3 and HTTP/3 QUIC relationship` — HTTP/3 uses TLS 1.3 handshake/key schedule integrated with QUIC (RFC 9001), not a separate TLS-over-TCP connection. TLS certificates authenticate the QUIC endpoint while transport behavior differs from TCP-based HTTPS.
- `TLS record confidentiality does not hide traffic timing or size` — TLS protects record contents and integrity, but packet lengths, timing, direction, and connection patterns can still leak information.
- `TLS record padding` — TLS 1.3 permits padding encrypted records to obscure some length information; padding consumes bandwidth and does not hide timing or all traffic analysis.
- `Certificate identity validation per RFC 9525` — Service identity verification uses the appropriate SAN identifier, such as dNSName for a DNS host or iPAddress for an IP literal. Path trust and service-name matching are separate checks.
- `Subject Common Name is not a valid service identity fallback` — Current RFC 9525 says not to use the certificate Subject Common Name to identify a service; validate the correctly typed SAN identity instead.
- `Wildcard certificate matching boundary` — A wildcard is constrained to the complete left-most DNS label under RFC 9525; it does not match arbitrary multiple labels or partial-label patterns.
- `TLS handshake` — The negotiation and authentication exchange that establishes shared traffic keys and connection parameters before protected application data. A failed handshake prevents a usable secure channel.
- `Server authentication` — The client obtains evidence that the server controls the private key associated with an accepted identity. This authenticates a service endpoint, not the human user logging in.
- `Certificate path validation` — The client checks whether a presented certificate can form an acceptable signed path to a trust anchor under its policy and current time/usage constraints. A mathematically valid signature alone is insufficient.
- `Trust anchor` — A locally trusted starting point for path validation, commonly configured through the client's trust store. The trust decision ultimately depends on client policy.
- `Subject Alternative Name (SAN)` — Certificate extension carrying identities, such as DNS names, against which the client can compare the requested host. Do not infer a match from the organization name or a different host in the chain.
- `Hostname verification` — The separate check that the identity requested by the client matches a certificate identity according to applicable rules. Disabling it defeats a central part of server authentication.
- `Certificate expiration` — A certificate is valid only within its encoded time interval under ordinary validation. Expiry can break every client connection even when no code changed; monitor renewal and deployment.
- `Certificate revocation status` — Information that a certificate may no longer be trusted before its end time. Clients and ecosystems vary in whether and how they obtain and enforce status, so do not promise uniform real-time revocation behavior.
- `OCSP stapling and revocation checking limitations` — OCSP stapling lets a server include a signed status response so clients need not contact the responder for every handshake. It can be stale, unavailable, or treated differently by clients; it does not create uniform hard-fail revocation behavior.
- `Forward secrecy` — A key-establishment property intended to limit retrospective disclosure of past sessions after later compromise of long-term authentication keys, under the protocol's assumptions. It does not defend compromised endpoints or leaked session secrets.
- `Cipher suite` — A named set of cryptographic choices negotiated for a TLS connection. TLS 1.3 uses a different, narrower cipher-suite organization than TLS 1.2; do not copy a TLS 1.2 suite string into TLS 1.3 configuration.
- `ALPN` — Application-Layer Protocol Negotiation, a TLS extension through which peers agree on an application protocol. Negotiating a protocol does not authorize a request.
- `SNI` — Server Name Indication, a TLS extension that lets a client indicate the intended hostname during handshake so a server can select an appropriate configuration/certificate. The client still verifies the returned identity.
- `TLS 1.3 early data (0-RTT) replay risk` — Resumption-based early application data may be replayed. Exclude unsafe state changes or design explicit replay defenses; ordinary application idempotency assumptions must be examined rather than presumed.
- `HTTP-to-HTTPS redirect` — A response that points a client from an HTTP URL to an HTTPS URL. Since the first request was cleartext, a redirect alone cannot protect it against interception or modification.
- `Mixed content` — An HTTPS page loading an HTTP resource. The insecure resource can undermine confidentiality or integrity of the page; browsers may block some kinds and treat others differently.

## Cross-item comparison
`TLS 1.2` and `TLS 1.3` are protocol versions, not interchangeable configuration labels. RFC 9846 specifies TLS 1.3 and updates requirements for TLS 1.2 implementations. `SNI` is visible in ordinary ClientHello; `ECH` encrypts the inner ClientHello but still exposes network/traffic metadata. A redirect acts after an HTTP request reaches a server; HSTS acts in a browser before later requests are sent. Certificate path failure and service-name mismatch require different diagnosis.

## Examples
If a browser requests `https://store.example` and the server presents a trusted chain for `login.example`, path validation may succeed while hostname verification fails. Correct the SAN identity; do not disable verification. If a POST transfers funds, do not permit it as early data without end-to-end replay defenses. ECH can conceal the true SNI from passive on-path observers when client, DNS/configuration, and server support it, but the destination IP and traffic pattern remain visible. RFC 9846 covers TLS behavior; [RFC 9849](https://www.rfc-editor.org/rfc/rfc9849.html) defines ECH; [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html) defines service identity.

## Common mistakes
- Treating encryption as proof of correct hostname or user authorization.
- Assuming every client checks revocation identically.
- Assuming early data is automatically safe because TLS protects it from network modification; replay is a different threat.
- Treating SNI as certificate verification or ALPN as authorization.
- Fixing certificate errors by suppressing validation rather than repairing identity, chain, time, or trust configuration.

## Knowledge checks with answers
1. A chain ends at a trusted root, but SAN excludes the URL host. **Reject: hostname verification fails.**
2. Does a redirect protect the original cleartext request? **No.** It only instructs the client after the request arrives.
3. What property makes 0-RTT special? **Potential replay of early data, especially dangerous for state-changing actions.**
