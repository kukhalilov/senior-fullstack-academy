## Scope and version

This reference describes the Dgraph distributed graph database and its DQL and GraphQL interfaces. The official documentation was checked 2026-11-20 and labels v25.5 as the latest DQL documentation version. Documentation version is not proof that every distribution or hosted offering has identical features; verify the server release, edition, deployment model and client compatibility you will run. Product status and release/support commitments should be evaluated before a new production adoption.

## How this group fits the mental model

Dgraph stores graph-shaped data as nodes connected by predicates/edges. It offers a low-level graph query language (DQL) and can generate a GraphQL API from a GraphQL schema. These are layered access paths over one graph store, not two independent databases. A GraphQL schema creates generated operations and can add API-facing rules; DQL gives more direct graph-query and mutation capabilities for advanced use cases.

At the distributed layer, Dgraph Zero coordinates membership, predicate-to-group assignment, timestamps and UID allocation. Dgraph Alpha nodes store graph data and serve requests. Alpha predicate groups and the Zero group use Raft for consensus and replication. Data distribution means one logical transaction can touch multiple predicates/groups, so latency and availability depend on distributed coordination and the relevant quorum. High availability requires enough replicas in each Raft group, persistent storage and careful failure-domain placement; running one Zero and one Alpha is not a highly available cluster.

## Supplied names explained

- **DQL (Dgraph Query Language)** — Dgraph's proprietary language for querying, mutating and deleting graph data. It is inspired by GraphQL but is neither a GraphQL superset nor a subset. DQL supports graph traversals, variables, recursion, filters, aggregation, facets, mutations and upserts. Use it when generated GraphQL operations do not express the required graph query. A DQL schema declares predicate types/indexes and node types; DQL node types are descriptive and are not automatically enforced as relational table constraints.
- **GraphQL schema and generated API** — Define types, fields, relationships and directives; Dgraph generates GraphQL operations and serves them at `/graphql`. Generated queries include get-by-ID, filtered/list and aggregate forms where supported; generated add/update/delete mutations depend on schema/configuration and `@generate`. This speeds CRUD development but can expose more operations than intended unless generation and auth are configured deliberately.
- **Generated queries and mutations** — Generated list operations include filter/order/pagination inputs only where field types have required support. Mutations can return nested selected fields and may invoke custom resolvers/lambdas. Do not treat generated mutation behavior as a substitute for a domain service when invariants require coordinated multi-step workflows, external side effects or authorization decisions.
- **Custom resolvers and Lambda** — Dgraph GraphQL can integrate external/custom resolver logic. DQL is also available for capabilities beyond the GraphQL API. Crossing to external services creates ordinary distributed-systems failure cases: timeouts, duplicate invocation, authorization propagation and partial success. Make side effects idempotent and avoid assuming a GraphQL mutation plus an external call is one atomic transaction.
- **Subscriptions** — GraphQL subscriptions can stream result changes to connected clients. They are stateful long-lived requests that retain document, variables and context; plan for connection capacity, auth expiry, reconnect/resubscribe, duplicate delivery and backpressure. A subscription is not a durable event log or a replacement for replayable messaging.
- **Predicates and schema** — A predicate names a scalar attribute or relationship. Declare types and cardinality intentionally; index only fields used by filtering/sorting/search because indexes consume storage and write work. Schema changes can trigger conversion/index construction; queries requiring a new index may fail until index computation completes. Dgraph supports `@index` tokenizers/functions, `@reverse` for reverse traversal, `@count` for edge counts, `@lang` for multilingual values and `@upsert` for conflict-aware uniqueness patterns. Exact supported tokenizer/functions depend on type and server release.
- **Indexes and search tokenizers** — Exact, term, full-text, trigram, hash, numeric, geo and other indexes support different operators and query patterns. An index is not implied by a field name: for example, sorting or inequality over strings requires an appropriate exact index according to the docs. Index creation has storage/build cost and may need backfill. Custom tokenizers are a plugin extension with deployment/version compatibility obligations.
- **Facets** — Metadata attached to an edge, such as relationship weight, date or status. A facet describes the relationship itself, not necessarily a property on the target node. Querying and filtering facets has its own syntax and indexing considerations; use them when the fact belongs to an edge (e.g. friendship since a date), not as a replacement for a first-class entity when the relationship has rich lifecycle or identity.
- **Transactions and conflicts** — Dgraph clients group queries/mutations into transactions. A transaction reads a consistent snapshot as of its start plus its own writes. Concurrent conflicting transactions can be aborted at commit; conflicts include writes to the same scalar predicate/node, a singular UID predicate, or an indexed predicate using `@upsert`. Aborted changes are discarded; client code must retry the entire logical operation with bounded backoff and ensure retry-safe behavior. Read-only transactions should be discarded/closed correctly, and mutations should be committed or explicitly aborted.
- **Upsert and uniqueness** — An upsert combines a query and mutation within a transaction to avoid a check-then-write race. `@upsert` on indexed fields causes conflicts for competing writes to the same value, but application semantics still need to handle an aborted transaction and choose the canonical identity. Never implement uniqueness as “query says absent, then insert” across two independent transactions.
- **Zero, Alpha and Raft groups** — Zero coordinates metadata and assignments; Alphas store/query data. The cluster has a Zero Raft group and one or more Alpha groups, with predicate ownership assigned to Alpha groups. Raft leader election and quorum replication protect a group within its configured failure model; loss of quorum makes that group unavailable for writes. Adding nodes does not by itself increase useful capacity if assignment/replicas, disk, network, query fan-out or rebalancing are the bottleneck.
- **GraphQL security** — Important default: Dgraph's GraphQL security documentation states that by default generated operations are accessible to anonymous clients unless authorization is configured. Define JWT validation, API-key policy, operation-level RBAC and data-level `@auth` rules; deny by default when appropriate. Check both query and mutation paths, custom resolvers, subscriptions, admin endpoints and direct DQL/gRPC access. Hiding a field in the frontend is not authorization.
- **Backup, restore and operations** — Build backups around the deployed version and supported backup/restore procedure, then test restore into an isolated cluster. Monitor Zero/Alpha health, Raft quorum/leadership, predicate-group assignment, disk, compaction, query latency, transaction aborts, index builds and subscription load. A replicated cluster is not an independent backup against operator deletion, corruption or region-wide failure.

## Cross-item comparison

Dgraph's generated GraphQL can reduce API boilerplate when the application maps cleanly to its schema. Neo4j offers its own graph model and Cypher ecosystem; Neptune offers managed AWS property-graph/RDF endpoints; relational databases can be more transparent for transactions and reporting when traversal depth is limited. Compare graph query expressiveness, constraints, indexes, transaction conflict behavior, client/runtime support, portability, operational maturity, backup guarantees, security defaults and total workload cost. Do not select a graph database solely because the domain has relationships: most data does.

## Examples

Model users and their followed users with a `follows` UID predicate. If the application frequently queries followers, declare `@reverse`; if it filters by relationship creation date or trust score, store a facet or promote the relationship to its own node when it needs identity, audit history, permissions or multiple attributes. Declare indexes for fields used in filters and wait for index construction before depending on them. For a follow operation, enforce self-follow and privacy rules in the server authorization/domain layer, then use a transaction with idempotent edge semantics. Retry transaction aborts by rerunning the full query-and-mutation, not just sending a stale mutation again.

For GraphQL deployment, start with a schema that generates only needed operations, configure `@auth`/JWT behavior and test anonymous requests before exposing the endpoint. If a mutation must also send a notification, commit the graph change first and use a durable outbox/event workflow; the graph transaction cannot atomically commit an email or arbitrary HTTP request.

## Common mistakes

- Assuming DQL and GraphQL are identical languages or independent storage systems.
- Exposing the generated `/graphql` endpoint while assuming anonymous access is disabled by default.
- Treating GraphQL schema declarations as database constraints without checking DQL enforcement and indexes.
- Assuming generated CRUD operations enforce every business invariant or coordinate external effects.
- Adding indexes to every predicate, ignoring build time, write amplification and disk cost.
- Using a read-then-insert uniqueness check outside one upsert transaction.
- Retrying only the final mutation after a transaction conflict instead of rerunning the whole transaction.
- Confusing an edge facet with a node property or a relationship entity with a simple annotation.
- Counting Raft replicas as protection from all failures, including shared-zone loss, logical deletion or bad restore procedures.
- Treating GraphQL subscriptions as durable replayable events.

## Knowledge checks with answers

1. **How do GraphQL and DQL relate?** GraphQL can be generated from a schema over Dgraph's graph store; DQL is a separate, proprietary lower-level language that can express graph operations beyond generated CRUD.
2. **What happens when two conflicting transactions commit concurrently?** One can be aborted; its changes are discarded. The client should retry the complete transaction safely.
3. **What does `@reverse` provide?** It builds reverse traversal support for a predicate so queries can efficiently navigate incoming edges, at additional index/storage cost.
4. **Why is an unconfigured generated GraphQL API risky?** The documentation says anonymous access is allowed by default unless authorization is configured; generated reads and writes can therefore be exposed.
5. **When should a relationship become its own node?** When the relationship needs stable identity, lifecycle, authorization, audit data or several independently managed attributes rather than a small edge annotation.
