# query processing execution plans cardinality and parameter sensitivity — Reference: Estimated and actual plans, operators, and execution properties

# Scope and version

Targets SQL Server 2025 (17.x), with compatibility and eligibility boundaries called out separately. Azure SQL products can expose different release/update policies. These are the exact names frozen for this reference group; consult the cited Microsoft reference for operators and options outside this curated list.

# Supplied names explained

| Exact inventory item | Meaning and important edge |
| --- | --- |
| `Estimated execution plan` | Compiled optimizer choice based on estimates; it does not execute the query and has no actual row counts or runtime warnings. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Actual execution plan` | The compiled plan plus observations from one completed execution. Parameter values, concurrency, cache state, and runtime conditions make it one sample, not a universal verdict. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Graphical plan` | A visual rendering of plan operators and properties. It is an interface over Showplan data, so preserve XML when you need machine-readable comparison. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Showplan XML` | Structured plan representation containing statement, operator, estimate, runtime, warning, and optimizer properties. Attributes evolve; parse defensively across engine releases. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/performance/display-and-save-execution-plans?view=sql-server-ver17)) |
| `Query plan` | A physical execution strategy chosen for a statement at compilation or variant compilation. Declarative SQL specifies results, not operator order. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Physical operator` | An implementation routine such as a seek, hash join, or sort. It is chosen to implement relational work and must be read with its inputs, row counts, executions, and properties. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Logical operator` | The relational operation required, such as join or aggregate, independent from the physical algorithm selected to implement it. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Table scan` | Reads a heap. It can be correct for broad access or a small table; scan presence alone is not evidence of a bad plan. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Index scan` | Reads some or all ordered index rows. It can satisfy ordering or be cheaper than many lookups when many rows qualify. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Index seek` | Navigates an index using seek predicates, but may still read many rows, apply residual predicates, or perform many lookups. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Key lookup` | Fetches base-row columns from a clustered index for each qualifying nonclustered entry. High execution count can dominate an apparently cheap seek. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `RID lookup` | Fetches a heap row using its row identifier for each qualifying nonclustered entry; repeated lookups can cost more than a scan. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Nested Loops join` | Often efficient when the outer input is small and the inner side has a useful access path. Repeated inner executions multiply cost when estimates are wrong. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Hash Match join` | Builds a hash structure from one input and probes it with another; suitable for larger unsorted inputs but sensitive to memory grant and spill. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Merge Join` | Consumes inputs ordered on join keys. It can be efficient at scale but may require sorting or may handle many-to-many matches with extra work. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Sort operator` | Orders rows for ORDER BY, merge, or another requirement. Large sorts need memory and can spill to tempdb; check actual rows and grant. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Stream Aggregate` | Aggregates ordered input, often with low memory; upstream ordering may be required. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Hash Aggregate` | Groups through a hash structure without requiring ordered input; memory pressure can produce spills. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Filter operator` | Tests a predicate after its input produces rows. Compare rows before and after it; a residual filter can mean the access path read more than it returned. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Compute Scalar` | Defines scalar expressions. The expression may be deferred until the value is needed, so the icon alone does not quantify CPU cost. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Spool operator` | Stores rows in a worktable for reuse, protection, or plan semantics. Determine its type, rebind/rewind counts, and whether it is a symptom or intentional reuse. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Exchange operator` | Moves rows among parallel workers. Distribution choice can create skew, synchronization, or data movement cost. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Parallelism operator` | Graphical label for exchange operations such as gather, repartition, and distribute streams; inspect worker counts and skew, not just the icon. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Actual row count` | Observed rows produced by an operator for an execution. Compare with estimated rows at cardinality-sensitive boundaries and account for per-thread display semantics. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Estimated row count` | Optimizer prediction used in cost and memory decisions. It is not a promise or a runtime measurement. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Actual execution count` | How often an operator ran. A small per-execution cost can be large when repeated thousands of times, especially under Nested Loops. | `Actual execution time` | Runtime measurement available in supported actual/live plans. It includes environmental effects and should be correlated with CPU, reads, waits, and concurrency. # How to use this reference

Read the plan from data-producing leaves toward the root, then trace what drives repeated work from root toward leaves. Compare estimated and actual rows at the first divergence; check executions, rows read versus returned, memory grant/spills, and runtime evidence. A seek, scan, warning, or high estimated cost is a clue, not a verdict.

# How this group fits the mental model

This inventory names the plan, estimate, or diagnostic surface needed to explain a query's behavior. Connect each property to a question: what did the optimizer predict, what happened at runtime, and where did the difference begin?

# Cross-item comparison

Estimated rows describe the forecast; actual rows describe one execution. A seek predicate navigates a key range; a residual predicate filters rows after access. A plan hash describes a shape; Query Store runtime intervals describe observed workload behavior. Use pairs together instead of treating any one as a score.

# Examples

If a Nested Loops inner seek executes 80,000 times, inspect Actual Executions and rows per execution even if the icon looks selective. If estimated rows at an upstream filter are 5 but actual rows are 40,000, trace statistics, parameter values, and predicates before blaming the downstream Hash Match spill.

# Common mistakes

- Calling every scan bad or every seek good.
- Comparing estimated subtree cost to elapsed milliseconds.
- Reading plan arrows as invocation direction; graphical flow and pull execution direction differ.
- Treating a warning as proof of a fix without checking the operator and runtime impact.

# Knowledge checks with answers

1. What is the earliest useful location for an estimate diagnosis? The first consequential estimated/actual row divergence.
2. Does an actual plan generalize to all values? No; it records one execution context.
3. What does a residual predicate imply? Rows can be read before the predicate rejects them; compare rows read and returned.
