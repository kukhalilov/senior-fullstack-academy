# query processing execution plans cardinality and parameter sensitivity — Reference: Estimated and actual plans, operators, and execution properties

# Scope and version

Targets SQL Server 2025 (17.x), with compatibility and eligibility boundaries called out separately. Azure SQL products can expose different release/update policies. These are the exact names frozen for this reference group; consult the cited Microsoft reference for operators and options outside this curated list.

# Supplied names explained

| Exact inventory item | Meaning and important edge |
| --- | --- |
| `Estimated execution plan` | Compiled optimizer choice based on estimates; it does not execute the query and has no actual row counts or runtime warnings. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Actual execution plan` | The compiled plan plus observations from one completed execution. Parameter values, concurrency, cache state, and runtime conditions make it one sample, not a universal verdict. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Graphical plan` | A visual rendering of plan operators and properties. It is an interface over Showplan data, so preserve XML when you need machine-readable comparison. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Showplan XML` | Structured plan representation containing statement, operator, estimate, runtime, warning, and optimizer properties. Attributes evolve; parse defensively across engine releases. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/performance/display-and-save-execution-plans?view=sql-server-ver17)) |
| `Query plan` | A physical execution strategy chosen for a statement at compilation or variant compilation. Declarative SQL specifies results, not operator order. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Physical operator` | An implementation routine such as a seek, hash join, or sort. It is chosen to implement relational work and must be read with its inputs, row counts, executions, and properties. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Logical operator` | The relational operation required, such as join or aggregate, independent from the physical algorithm selected to implement it. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Table scan` | Reads a heap. It can be correct for broad access or a small table; scan presence alone is not evidence of a bad plan. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Index scan` | Reads some or all ordered index rows. It can satisfy ordering or be cheaper than many lookups when many rows qualify. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Index seek` | Navigates an index using seek predicates, but may still read many rows, apply residual predicates, or perform many lookups. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Key lookup` | Fetches base-row columns from a clustered index for each qualifying nonclustered entry. High execution count can dominate an apparently cheap seek. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `RID lookup` | Fetches a heap row using its row identifier for each qualifying nonclustered entry; repeated lookups can cost more than a scan. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Nested Loops join` | Often efficient when the outer input is small and the inner side has a useful access path. Repeated inner executions multiply cost when estimates are wrong. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Hash Match join` | Builds a hash structure from one input and probes it with another; suitable for larger unsorted inputs but sensitive to memory grant and spill. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Merge Join` | Consumes inputs ordered on join keys. It can be efficient at scale but may require sorting or may handle many-to-many matches with extra work. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Sort operator` | Orders rows for ORDER BY, merge, or another requirement. Large sorts need memory and can spill to tempdb; check actual rows and grant. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Stream Aggregate` | Aggregates ordered input, often with low memory; upstream ordering may be required. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Hash Aggregate` | Groups through a hash structure without requiring ordered input; memory pressure can produce spills. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Filter operator` | Tests a predicate after its input produces rows. Compare rows before and after it; a residual filter can mean the access path read more than it returned. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Compute Scalar` | Defines scalar expressions. The expression may be deferred until the value is needed, so the icon alone does not quantify CPU cost. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Spool operator` | Stores rows in a worktable for reuse, protection, or plan semantics. Determine its type, rebind/rewind counts, and whether it is a symptom or intentional reuse. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Exchange operator` | Moves rows among parallel workers. Distribution choice can create skew, synchronization, or data movement cost. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Parallelism operator` | Graphical label for exchange operations such as gather, repartition, and distribute streams; inspect worker counts and skew, not just the icon. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Actual row count` | Observed rows produced by an operator for an execution. Compare with estimated rows at cardinality-sensitive boundaries and account for per-thread display semantics. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Estimated row count` | Optimizer prediction used in cost and memory decisions. It is not a promise or a runtime measurement. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Actual execution count` | How often an operator ran. A small per-execution cost can be large when repeated thousands of times, especially under Nested Loops. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Actual execution time` | Runtime measurement available in supported actual/live plans. It includes environmental effects and should be correlated with CPU, reads, waits, and concurrency. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Actual logical reads` | Pages requested from the buffer pool, reported through statistics I/O for statements/tables. Compare consistent runs and do not confuse logical with physical disk reads. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Memory grant` | Execution memory reserved for operators such as sort/hash. Too small can spill; too large can reduce concurrency. Compare requested, granted, and used amounts. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Spill to tempdb` | A sort/hash or other operator writes work to tempdb because memory was insufficient or execution shape required it. Find the operator, spill volume, estimate error, and grant feedback. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Residual predicate` | Predicate evaluated after rows are located by the access method; rows can be read then discarded, so inspect actual rows read versus returned. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Seek predicate` | Predicate used to navigate index key ranges. A seek predicate can be broad and can coexist with residual predicates. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Predicate property` | Showplan property describing the filter condition applied by an operator. Distinguish it from Seek Predicates to see which conditions narrowed navigation. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Plan warning` | A diagnostic annotation such as spill, conversion, or missing statistics. It identifies a lead to investigate; it is not itself a diagnosis or an automatic repair instruction. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Adaptive Join` | In batch mode, delays choosing Hash Match versus Nested Loops until it scans the build input and compares its rows with a threshold in the plan. It can avoid a poor join choice when cardinality is uncertain, but only eligible plans use it and the runtime choice still depends on input size. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/performance/intelligent-query-processing?view=sql-server-ver17)) |
| `Bitmap operator` | A compact membership filter built from one join input and applied to another, often before an exchange or scan in a parallel plan. It can discard rows that cannot match early; inspect whether it is build/probe side and do not confuse it with a user-visible result filter. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Concatenation operator` | Combines input streams without removing duplicates, commonly implementing UNION ALL or branches of rewrites. It preserves the meaning of the branches; if duplicate elimination is required, look for an additional distinct/sort/hash operation. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Constant Scan` | Produces a small constant rowset without reading a user table. The optimizer uses it for constant values, empty/default rows, and as support for some scalar or DML plan shapes; its presence alone is not a table read. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Top operator` | Stops requesting rows from its child when the requested count/row goal is satisfied, so a scan beneath TOP can stop early. WITH TIES, ordering, and row-goal costing affect behavior; check whether an ORDER BY defines deterministic selection. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Sequence Project` | Computes per-row expressions that depend on ordered sequence metadata, such as row numbers or other windowing support. Its input often needs a Sort or ordered access; inspect partition/order keys and upstream rows. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Window Aggregate` | Evaluates window aggregates over partition/order frames, potentially in batch mode. Required ordering, frame size, and partition distribution determine upstream sort/work; it does not collapse rows like GROUP BY. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Index Spool` | Materializes rows into a temporary indexed worktable, then probes that worktable for repeated lookups. It may reduce repeated base-table work but incurs tempdb writes/build cost; inspect rebinds, rewinds, and whether a permanent index or rewrite is justified. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Table Spool` | Stores rows in a worktable for reuse or to preserve semantics. It can protect Halloween-sensitive modifications or support repeated inner input; determine why it exists and measure its writes/reads before trying to remove it. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Eager Spool` | Reads and stores its entire input before returning rows to the parent. This can prevent repeated work or protect correctness, but may add latency, memory, and tempdb I/O; it differs from Lazy Spool's on-demand fill. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Lazy Spool` | Stores rows as the parent requests them, allowing later rewinds to reuse already-read rows. Rebinds can require rebuilding for changed correlated values; compare Actual Rebinds and Actual Rewinds to understand savings/cost. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Distribute Streams` | Exchange operator that sends rows from one producer stream across parallel consumer streams, commonly round-robin or according to a distribution requirement. Inspect per-thread row counts for skew and include exchange movement/synchronization in the cost analysis. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Repartition Streams` | Exchange that redistributes rows among workers using a partitioning key or other distribution. Hash-key skew can leave one worker doing most of the work; compare per-thread rows and upstream key distribution. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Gather Streams` | Exchange that combines rows from multiple parallel workers into one consumer stream. It can be a serial bottleneck when one downstream operator must process all rows; examine worker completion skew and rows gathered. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Row mode execution` | Processes rows individually through operators. Row mode is appropriate for many OLTP and low-row-count plans; batch mode is not inherently faster for every query or data size. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Batch mode execution` | Processes a vector of rows per operator call, reducing per-row overhead and often helping analytics. SQL Server can use batch mode with rowstore in eligible plans; mixed batch/row regions and conversion costs can affect benefit. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Actual Rebinds` | Number of times an operator is reopened with changed correlated parameters, requiring its inner result to be reevaluated. Especially relevant on the inner side of Nested Loops; compare with estimated rebinds and work per rebind. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Actual Rewinds` | Number of times an operator is reopened with unchanged correlated parameters, allowing prior results to be reused where supported. A high rewind count can indicate successful spool reuse or repeated access; interpret with operator type and row volume. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Actual EndOfScans` | Counts how often an operator reaches the end of its input stream. For an inner Nested Loops subtree it can be reached repeatedly; compare with rebind/rewind counts and do not interpret as the number of table scans across the whole query. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |
| `Estimated subtree cost` | Optimizer's modeled cumulative cost for an operator and its descendants, in internal cost units. It helps rank alternatives within the same optimization context but is not elapsed time, CPU milliseconds, or a reliable comparison across machines/workloads. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/performance/cardinality-estimation-sql-server?view=sql-server-ver17)) |
| `CardinalityEstimationModelVersion property` | Showplan statement property identifying the CE model used, such as 70, 120, 150, 160, or 170. It helps identify which model produced estimates; it does not tell whether the estimate is correct or which specific assumption caused error. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/performance/cardinality-estimation-sql-server?view=sql-server-ver17)) |
| `StatementOptmLevel property` | Showplan statement property indicating optimization level, commonly FULL or TRIVIAL. TRIVIAL means the optimizer found a plan without full cost-based search; it is not a warning that the plan is poor. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/performance/query-processing-architecture-guide?view=sql-server-ver17)) |
| `StatementOptmEarlyAbortReason property` | Explains why full optimization stopped early, such as reaching a good-enough plan or a search limit. An early-abort reason is context for plan exploration, not proof the chosen plan is wrong; compare actual workload evidence. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/performance/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Plan-affecting convert warning` | Warns that an implicit or explicit conversion may affect cardinality estimation or index access. Inspect the expression, data types, and which side is converted; some conversions preserve seeks, so confirm the actual access predicate and reads. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/query-processing-architecture-guide?view=sql-server-ver17)) |
| `Operator execution mode` | Showplan property identifying row or batch processing for an operator. A query can mix modes; use it to explain CPU/throughput behavior, while measuring the full plan rather than assuming batch always wins. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/performance/intelligent-query-processing?view=sql-server-ver17)) |
| `Actual rows per execution` | Rows produced in an individual operator execution, distinct from total rows when that operator runs repeatedly. Pair it with ActualExecutions and parallel-thread details; total work can be large even when per-invocation rows are small. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference?view=sql-server-ver17)) |

# How to use this reference

Read the plan from data-producing leaves toward the root, then trace what drives repeated work from root toward leaves. Compare estimated and actual rows at the first divergence; check executions, rows read versus returned, memory grant/spills, and runtime evidence. A seek, scan, warning, or high estimated cost is a clue, not a verdict.

# How this group fits the mental model

This inventory names the plan, estimate, or diagnostic surface needed to explain a query's behavior. Connect each property to a question: what did the optimizer predict, what happened at runtime, and where did the difference begin?

# Cross-item comparison

Estimated rows describe the forecast; actual rows describe one execution. A seek predicate navigates a key range; a residual predicate filters rows after access. A plan hash describes a shape; Query Store runtime intervals describe observed workload behavior. Use pairs together instead of treating any one as a score.

# Examples

If a Nested Loops inner seek executes 80,000 times, inspect Actual Executions and rows per execution even if the icon looks selective. If estimated rows at an upstream filter are 5 but actual rows are 40,000, trace statistics, parameter values, and predicates before blaming the downstream Hash Match spill.

# Common mistakes

- Calling every scan bad or every seek good.
- Comparing estimated subtree cost to elapsed milliseconds.
- Reading plan arrows as invocation direction; graphical flow and pull execution direction differ.
- Treating a warning as proof of a fix without checking the operator and runtime impact.

# Knowledge checks with answers

1. What is the earliest useful location for an estimate diagnosis? The first consequential estimated/actual row divergence.
2. Does an actual plan generalize to all values? No; it records one execution context.
3. What does a residual predicate imply? Rows can be read before the predicate rejects them; compare rows read and returned.
