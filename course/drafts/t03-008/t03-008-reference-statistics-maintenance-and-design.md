# indexes types covering indexes index maintenance and statistics — Reference: Statistics, workload fit, maintenance, and design decisions

# Scope and version

Targets SQL Server 2025 (17.x) Database Engine rowstore/index/statistics semantics. Cloud platforms, editions, and specialized index availability can differ. Vector indexes are preview in SQL Server 2025; JSON indexes and ordered nonclustered columnstore indexes are current GA capabilities. See the cited version sources.

# How this group fits the mental model

This is one bounded slice of the full index lifecycle: the exact supplied names are explained below, then connected back to query workload, optimizer estimates, and write cost.

# Supplied names explained

| Exact inventory item | Meaning, behavior, and important edge |
| --- | --- |
| `Index statistics` | Statistics summarize key distribution for the optimizer and are created for indexes. They influence cardinality estimates, not data correctness; stale or unrepresentative stats can cause poor plans even when the index structure is healthy. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `Histogram` | A statistics histogram describes distribution for only the first statistics key column, with at most 200 steps. It is sampled or full-scan data and cannot represent arbitrary correlations among several columns. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `Density vector` | Statistics density values summarize distinctness for key prefixes and help estimate equality combinations. They complement the first-column histogram but are not a multi-dimensional histogram or guarantee of accurate correlation estimates. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-vector-index-transact-sql?view=sql-server-ver17)) |
| `Auto-created statistics` | With AUTO_CREATE_STATISTICS ON, the optimizer can create single-column statistics for predicate columns when useful. These statistics do not automatically solve cross-column correlation and are visible through sys.stats (often with _WA names). ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `Filtered statistics` | Statistics created with a WHERE predicate describe a relevant subset and can improve estimates when query predicates match that subset. They are separate from an index and may be useful even without a filtered index. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `Statistics update threshold` | SQL Server marks statistics stale based on modifications and table cardinality; the threshold varies by engine version and compatibility level. Do not hardcode a single “20 percent” rule for current large tables. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `AUTO_UPDATE_STATISTICS` | When ON, the optimizer can refresh stale statistics before compilation/execution. Turning it off leaves stale estimates until manual maintenance and often harms plans; statistics updates can trigger recompilation. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `AUTO_UPDATE_STATISTICS_ASYNC` | When ON with auto-update enabled, a query can compile using existing statistics while an asynchronous update runs, avoiding waiting for that update but allowing the first plan to use old estimates. It is a workload tradeoff, not universally faster. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `CREATE STATISTICS` | Creates manual column or filtered statistics independently of an index. Choose leading columns based on predicates and use documented sampling/fullscan options; each statistics object supports up to 64 columns but only the leading column has a histogram. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-statistics-transact-sql?view=sql-server-ver17)) |
| `UPDATE STATISTICS` | Refreshes a statistics object or table/index statistics with sampling or FULLSCAN choices. It can improve estimates but causes plan recompilation and consumes I/O/CPU; do not update everything repeatedly without evidence. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/update-statistics-transact-sql?view=sql-server-ver17)) |
| `sp_updatestats` | A database-scoped stored procedure that updates statistics on user-defined and internal tables according to its modification logic. It is a broad maintenance tool, not equivalent to a targeted full scan of every object. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/update-statistics-transact-sql?view=sql-server-ver17)) |
| `Reorganize index` | ALTER INDEX ... REORGANIZE incrementally defragments eligible rowstore leaf pages and is online, but does not rebuild the full tree or refresh index statistics. It may be paused/resumed only within its own execution semantics and is not a universal response to low density. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/reorganize-and-rebuild-indexes?view=sql-server-ver17)) |
| `Rebuild index` | ALTER INDEX ... REBUILD recreates the index, can change fill/compression options, and refreshes that index’s statistics as a side effect. It can require substantial CPU, I/O, log, workspace, and locks; ONLINE/resumable support is conditional. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/alter-index-transact-sql?view=sql-server-ver17)) |
| `ALTER INDEX REORGANIZE` | The T-SQL maintenance operation that compacts/reorders rowstore leaf pages incrementally. It is less resource-intensive than rebuild in many cases but does not correct every issue or update statistics; columnstore reorganize has separate rowgroup merge behavior. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/reorganize-and-rebuild-indexes?view=sql-server-ver17)) |
| `ALTER INDEX REBUILD` | The T-SQL operation to recreate one or all indexes. It can run ONLINE when supported, and RESUMABLE only for supported online operations; syntax/options and impact differ by index kind and edition. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/alter-index-transact-sql?view=sql-server-ver17)) |
| `Index usage statistics` | Usage counters record seeks, scans, lookups, updates, and last-use times. They reset on engine restart and omit some index types; combine them with a representative business cycle and write costs before dropping an index. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `sys.dm_db_index_usage_stats` | Returns per-index user/system seeks, scans, lookups, updates, and last operation times. Counters reset on restart and are not evidence of full workload history; permissions and cloud tenant filtering apply, and memory-optimized/spatial usage is not reported here. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-index-usage-stats-transact-sql?view=sql-server-ver17)) |
| `Index operational statistics` | Lower-level access, lock, and latch counters by partition, available through operational DMVs. They help diagnose contention or maintenance patterns but are snapshots/counters, not direct proof that a proposed index fixes a workload. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `sys.dm_db_index_operational_stats` | A function returning partition-level row/page access, locking, latching, and allocation activity for indexes. Counters can reset as metadata ages/reloads; permission and version details matter, so correlate with sampling window and workload. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-index-operational-stats-transact-sql?view=sql-server-ver17)) |
| `Missing-index DMV recommendation boundary` | Optimizer missing-index requests are transient, incomplete suggestions generated during optimization. They do not account for all existing/overlapping indexes, write costs, included-column limits, or workload priorities; consolidate and test before deployment. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `Index write amplification` | Each extra index may need maintenance for a row change, adding log volume, CPU, I/O, locks/latches, and storage. An index that speeds reads can lower write throughput and increase backup/cache footprint. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `Over-indexing` | Redundant, unused, or overly wide indexes duplicate storage and write work, slow schema changes, and compete for cache. Before dropping one, examine overlap, constraints, filtered predicates, rare critical queries, resets, and a complete usage period. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `SARGable predicate` | A predicate is search-argument-friendly when the optimizer can use an index key to seek a bounded range. Wrapping the indexed column in a function or forcing incompatible conversions can prevent a seek; preserve semantics and verify the actual plan. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `Left-prefix key use` | A composite B+ tree can efficiently seek from leading key prefixes; gaps or predicates only on later keys usually require scanning more of the index. A different index or optimizer strategy may help, but there is no rule to index every predicate column first. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `Covering index` | An index covers a query when it contains all required search, join, grouping/order, and output data, so no base-row lookup is needed. Covering can reduce reads but wide indexes increase storage and DML cost. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `Lookup avoidance tradeoff` | Adding INCLUDE columns can eliminate repeated key/RID lookups, but a scan may already be cheaper for many matches and wider indexes cost more on every write. Compare actual row counts, reads, CPU, and write impact. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `Parameter-sensitive selectivity` | A single cached plan may be poor when parameter values select radically different row counts. Index design interacts with this, but diagnose parameter-sensitive plan behavior and Query Store/PSP features separately instead of proliferating indexes blindly. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `Index maintenance window` | Plan maintenance around workload concurrency, log capacity, tempdb/workspace, replica/availability lag, edition support, and lock waits. Use measured page density and query impact, not a calendar or universal fragmentation threshold alone. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `AUTO_CREATE_STATISTICS` | Database option that lets the optimizer create single-column predicate statistics as needed. It does not create filtered statistics or multi-column correlation histograms. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `AUTO_DROP statistics option` | Statistics option that permits SQL Server to drop manually created statistics when they block schema changes. SQL Server 2022 enables auto-drop by default for new/migrated databases; inspect exact object settings before relying on it. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-stats-transact-sql?view=sql-server-ver17)) |
| `FULLSCAN statistics option` | Reads all rows for statistics rather than a sample, potentially improving distribution fidelity at greater I/O/CPU cost. It still produces the same histogram shape limits. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `SAMPLE statistics option` | Builds statistics from a sampled percentage/row count. It is cheaper than full scan but may miss skew or rare values; use repeatable evidence to choose sampling. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `RESAMPLE statistics option` | Reuses the last sampling rate when refreshing statistics. It may preserve a low-quality sample; verify prior sampling before assuming it means full scan. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `NORECOMPUTE statistics option` | Prevents automatic update for a statistics object. Stale statistics can harm plans; only disable with explicit monitoring and scheduled refresh. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `PERSIST_SAMPLE_PERCENT` | Persists a selected statistics sample percentage for later updates that omit a sampling clause, supported from SQL Server 2016 SP1 CU4 and later applicable products. It can be changed or reset with statistics DDL. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `INCREMENTAL statistics option` | Stores per-partition stats for supported partitioned objects, enabling targeted incremental updates. Some statistics operations/features are incompatible; check ALTER/UPDATE STATISTICS syntax. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `DBCC SHOW_STATISTICS` | Displays header, density vector, and histogram information for a statistics object. The SHOW_STATISTICS permission requirement and output reflect a sampled/dated snapshot, not the optimizer’s entire estimation model. ([source](https://learn.microsoft.com/en-us/sql/t-sql/database-console-commands/dbcc-show-statistics-transact-sql?view=sql-server-ver17)) |
| `sys.stats` | Catalog view with one row per statistics object, including index and column statistics. Join with sys.stats_columns and object metadata to map keys; permissions limit visible metadata. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-stats-transact-sql?view=sql-server-ver17)) |
| `sys.stats_columns` | Maps statistics objects to their ordered columns, allowing you to see which is the histogram-leading column and the statistic key sequence. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-stats-columns-transact-sql?view=sql-server-ver17)) |
| `sys.dm_db_stats_properties` | Returns last update, row count, sample size, modification counter, and related properties for one statistics object in the current database. It is point-in-time evidence, not an automatic rule for update. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-db-stats-properties-transact-sql?view=sql-server-ver17)) |
| `sys.dm_db_incremental_stats_properties` | Returns per-partition properties for incremental statistics. Use it to target affected partitions while respecting incremental-statistics eligibility and partition lifecycle. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `STATS_DATE` | Returns the date the specified statistics object was last updated, or NULL where metadata is absent/not visible. Pair it with modification counts and distribution evidence; age alone is not proof of staleness. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)) |
| `UPDATE STATISTICS index and table scopes` | UPDATE STATISTICS can refresh a named statistics object, all stats on an index, or table statistics using documented syntax. Scope and sampling clauses affect cost and plan recompilation. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/update-statistics-transact-sql?view=sql-server-ver17)) |
| `Statistics persisted for readable secondaries` | SQL Server 2025 can persist statistics created/updated on readable secondary replicas so read workloads can retain their stats. This is a release-specific behavior; follow the feature documentation for replica role and permissions. ([source](https://learn.microsoft.com/en-us/sql/sql-server/what-s-new-in-sql-server-2025?view=sql-server-ver17)) |
| `SQL Server 2025 full-text component version 2 migration` | SQL Server 2025 removes version 1 word-breaker, stemmer, and filter binaries from the installation. Migrate/rebuild indexes to version 2; new tokenization can change search matches, so test application search behavior as well as successful population. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/search/full-text-index-version-upgrade?view=sql-server-ver17)) |
| `FULLTEXT_INDEX_VERSION configuration` | Database-scoped configuration controlling the full-text component version used for index creation/rebuild. SQL Server 2025 defaults new indexes to version 2; retaining version 1 requires legacy binaries and is a compatibility workaround, not the forward path. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/search/full-text-index-version-upgrade?view=sql-server-ver17)) |
| `sys.fulltext_indexes.index_version` | The catalog column identifies whether a full-text index uses version 1 or 2 components. After an in-place SQL Server 2025 upgrade, inventory version 1 indexes and plan migration because searches/populations can fail when legacy binaries are absent. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/search/full-text-index-version-upgrade?view=sql-server-ver17)) |
| `MAXDOP statistics option` | Limits parallelism for supported CREATE/UPDATE STATISTICS operations, subject to workload-group and engine limits. It may reduce contention while increasing completion time. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `Filtered statistics WHERE predicate` | Creates statistics for rows satisfying a restricted simple predicate. It can describe a subset without creating an index, but the query needs compatible predicates for useful estimates. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `UPDATE STATISTICS ON PARTITIONS` | For incremental statistics, RESAMPLE can target partition numbers/ranges with ON PARTITIONS. This is not valid for every statistics object; require eligible partitioned statistics. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/update-statistics-transact-sql?view=sql-server-ver17)) |
| `UPDATE STATISTICS ALL COLUMNS INDEX scope` | The ALL, COLUMNS, and INDEX scopes select classes of statistics on the table. Use the named-statistics form for targeted work and avoid assuming ALL means every sampling strategy is optimal. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/update-statistics-transact-sql?view=sql-server-ver17)) |
| `CREATE STATISTICS 64-column limit` | A statistics object can list up to 64 columns. The column order is meaningful: only the first column receives a histogram, while all key prefixes contribute density information. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-statistics-transact-sql?view=sql-server-ver17)) |

# Cross-item comparison

Statistics estimate data shape; usage DMVs measure a limited counter interval; operational statistics expose lower-level activity. Reorganize and rebuild alter physical structure differently, while query shape and write amplification determine whether a new index is worthwhile.

# Examples

Use the examples in the overview and concepts with your own representative query and data distribution. A DDL statement creating an index proves only that the structure exists; compare actual row counts, reads, writes, and plan alternatives before retaining it.

# Common mistakes

- Adding every suggested missing index independently.
- Treating key order as irrelevant or placing all columns in INCLUDE.
- Dropping an index because counters are zero shortly after restart.
- Rebuilding every index on an arbitrary schedule.
- Assuming online means no locks or resource impact.
- Applying rowstore fragmentation advice to columnstore or memory-optimized indexes.
- Treating SQL Server 2025 vector preview as a stable cross-platform feature.

# Knowledge checks with answers

1. **What is the first experiment before adding a key?** Measure representative query shape, selectivity, reads, writes, and actual estimates.
2. **How do you distinguish rowstore from columnstore?** Rowstore B+ tree entries are row-oriented; columnstore stores compressed per-column segments grouped into rowgroups.
3. **What does a filtered index save?** It can avoid storing rows outside its predicate, reducing size and maintenance if queries imply the filter.
4. **What does rebuild do to index stats?** Recreating the index refreshes its statistics as a side effect.
5. **What does the usage DMV miss?** Full lifetime history and some specialized index types, including spatial and memory-optimized usage.
