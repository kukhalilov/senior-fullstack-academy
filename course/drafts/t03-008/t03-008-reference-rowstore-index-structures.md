# indexes types covering indexes index maintenance and statistics — Reference: Clustered and nonclustered rowstore indexes

# Scope and version

Targets SQL Server 2025 (17.x) Database Engine rowstore/index/statistics semantics. Cloud platforms, editions, and specialized index availability can differ. Vector indexes are preview in SQL Server 2025; JSON indexes and ordered nonclustered columnstore indexes are current GA capabilities. See the cited version sources.

# How this group fits the mental model

This is one bounded slice of the full index lifecycle: the exact supplied names are explained below, then connected back to query workload, optimizer estimates, and write cost.

# Supplied names explained

| Exact inventory item | Meaning, behavior, and important edge |
| --- | --- |
| `Clustered index` | Its leaf level is the table data, ordered by the clustered key; a table can have at most one. Select a narrow, stable, unique, preferably increasing key when it fits access and write patterns, because every nonclustered index uses the clustered key as its row locator. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Nonclustered index` | A separate B+ tree stores key values and row locators. It can support seeks, ordered access, and covering plans, but every extra index consumes pages and adds work to INSERT, UPDATE, DELETE, logging, and backups. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Heap` | A table without a clustered index stores rows in an unordered heap. Nonclustered row locators are RIDs; forwarding records can arise when an updated row no longer fits its page. A heap is not automatically wrong, but understand lookup and maintenance consequences. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Index key` | Key columns establish B+ tree ordering and search boundaries. Their order matters: equality predicates on leading keys followed by range/order predicates are common useful shapes; key width affects every level and locator usage. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Included column` | A nonkey column stored only at a nonclustered index leaf can cover projection without increasing key width or ordering. It cannot support seek/order semantics as a key can, and wide includes still cost storage and DML. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Leaf level` | The lowest B+ tree level contains the index entries; clustered leaf pages contain table rows, while nonclustered leaves contain key, locator, and optional included values. Covering data lives here. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `B-tree` | The documentation term for SQL Server rowstore indexes; the engine implements a B+ tree with root/intermediate navigation and linked leaf pages. Do not apply this structure to columnstore or memory-optimized indexes. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Root page` | The top navigation page of a rowstore B+ tree. A seek starts here and descends through intermediate pages to the matching leaf range. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Intermediate page` | A nonleaf B+ tree page that maps key ranges to lower pages. More levels mean more navigation I/O, often affected by row count, key width, and page density. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Leaf page` | A lowest-level page containing rowstore index records. Clustered-index leaf records are the table rows; nonclustered leaf records carry row locators and may contain included columns. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Clustered key as row locator` | A nonclustered index on a clustered table locates rows by the clustered key. A wide clustered key is replicated into nonclustered row locators (with engine-specific uniquifier details for nonunique clustered keys), so its width multiplies storage and write costs. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `RID lookup` | A lookup from a nonclustered index entry to a heap row by its row identifier. Many repeated RID lookups can be expensive; a scan or a covering index may cost less. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Key lookup` | A lookup from a nonclustered index to the clustered row by clustered key, commonly shown as Key Lookup in plans. Its repeated cost depends on qualifying row count; do not add includes without measuring lookup versus write/storage cost. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Composite index key order` | The key is lexicographically ordered by declared column sequence. Equality on the leading key(s) can narrow the range, while a predicate only on a later key often cannot seek efficiently unless other plan features apply. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Ascending index key` | ASC orders a key from low to high. A backward scan can often satisfy a fully reversed ordering, but mixed direction requirements and predicates must match the key ordering and plan needs. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Descending index key` | DESC stores that key in reverse value order. It can support query ordering such as newest-first and mixed ASC/DESC composites; it does not make a query faster by itself. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Unique index` | Enforces distinct key tuples during every write, independently of application prechecks. It can be clustered or nonclustered and may be filtered; duplicates in multirow DML cause statement failure unless IGNORE_DUP_KEY behavior applies to inserts. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Unique clustered index` | A clustered index whose key is unique and whose leaf is the table data. SQL Server can add a hidden uniquifier for duplicate keys in a nonunique clustered index; declaring a suitable unique key avoids that ambiguity and can make locators smaller. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Primary-key backing index` | A PRIMARY KEY constraint creates a unique index, clustered by default only when no clustered index already exists. Specify clustered/nonclustered deliberately because the logical key and physical row organization are separate choices. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/clustered-and-nonclustered-indexes-described?view=sql-server-ver17)) |
| `Fill factor` | A percentage of leaf-page fullness requested at index create/rebuild, leaving room for future inserts at the cost of more pages and I/O. It is not continually maintained; Microsoft recommends 0/100 in most cases unless measured page splits justify a lower value. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `PAD_INDEX` | When ON, applies the fill-factor free-space percentage to intermediate index pages as well as leaf pages. It has effect only with a nonzero FILLFACTOR and may increase tree size; tune only from evidence. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Index page split` | A full page may split to accommodate an insert or key update. Splits add logging and can lower page density; random insert keys can cause widespread splits, while monotonically increasing keys can create last-page contention. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Index fragmentation` | For rowstore, logical page order differs from physical page order. It can increase I/O for scans, but page density, access pattern, cache, and workload matter; a fragmentation percentage alone is not a maintenance decision. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Index compression ROW` | ROW compression reduces storage using variable-length representations and metadata savings. It can reduce I/O but adds CPU; evaluate real data and workload, and distinguish rowstore compression from columnstore compression. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Index compression PAGE` | PAGE compression adds prefix and dictionary compression after row compression for additional savings, often at greater CPU cost. It is supported for eligible rowstore indexes/partitions; columnstore uses its own compression modes. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Online index operation` | ONLINE reduces blocking for supported index operations but still takes brief locks at phases and consumes resources. Availability depends on operation, index type, edition, and product; it does not mean zero blocking. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/guidelines-for-online-index-operations?view=sql-server-ver17)) |
| `Resumable index operation` | RESUMABLE allows supported online create/rebuild operations to pause and resume after interruption or a chosen duration. It requires ONLINE, retains an in-progress operation and its resource footprint, and has operation/version restrictions. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/guidelines-for-online-index-operations?view=sql-server-ver17)) |
| `CREATE INDEX` | Creates a relational rowstore index with declared key columns, optional INCLUDE columns, an optional filter, build options, and placement. It creates an access structure; it does not force optimizer use. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `CREATE UNIQUE INDEX` | Creates an index that also rejects duplicate key tuples. With IGNORE_DUP_KEY ON, duplicate rows in INSERT may be skipped with a warning; do not mistake this for upsert or general duplicate handling. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `CREATE CLUSTERED INDEX` | Creates the table’s one clustered rowstore organization. Building/rebuilding it sorts and moves the table data and needs workspace; changing the clustered key can rebuild nonclustered locators. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `CREATE NONCLUSTERED INDEX` | Creates a separate rowstore tree. Add ordered key columns for search/order and limited INCLUDE columns for coverage; check key byte/count limits and workload write cost. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `INCLUDE clause` | Adds nonkey columns at a nonclustered leaf level. Included values do not count against index key width/column limits but increase leaf storage; some types are excluded and computed columns have eligibility rules. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Filtered index WHERE clause` | Restricts a nonclustered index to rows satisfying a supported predicate. Query implication and required SET options control optimizer eligibility; a parameterized predicate may not prove a fixed filter. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/filtered-indexes?view=sql-server-ver17)) |
| `DROP_EXISTING` | Rebuilds a named existing index as part of CREATE INDEX, allowing changes to key/options without a separate drop gap. Clustered-key changes can affect row locators and alignment; do not assume every definition change is online or preserves physical placement. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `SORT_IN_TEMPDB` | Uses tempdb for intermediate sort results during supported index builds. It can reduce pressure on the user database filegroup but needs tempdb space and I/O; it is not supported for resumable index operations. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `IGNORE_DUP_KEY` | For a unique index, ON ignores duplicate rows in an INSERT while accepting nonduplicates and reporting a warning; duplicate rows can fail the statement when OFF. UPDATE semantics and multirow outcomes require careful application handling. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `STATISTICS_NORECOMPUTE index option` | Disables automatic statistics updates for the statistics associated with an index. It can leave stale estimates; use only with a deliberate external statistics process. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `STATISTICS_INCREMENTAL index option` | Creates per-partition statistics for eligible partitioned index statistics. It can allow targeted partition stats maintenance, but the statistics type and partition design must support incremental updates. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/statistics/statistics?view=sql-server-ver17)) |
| `ALLOW_ROW_LOCKS` | Controls whether the engine may use row locks for the index; ON permits but does not force row locking. Turning it OFF can increase blocking or broader lock use. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `ALLOW_PAGE_LOCKS` | Controls whether the engine may use page locks for the index; ON permits the optimizer/engine to choose them. Turning it OFF can affect locking and make reorganize unavailable for some cases. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `OPTIMIZE_FOR_SEQUENTIAL_KEY` | SQL Server 2019+ option that helps reduce last-page insert contention for sequential-key workloads. It does not remove all contention and may not help random or read-heavy patterns. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `MAXDOP index option` | Caps or delegates parallelism for an index operation, subject to configuration, workload, and edition. A lower value can reduce contention but lengthen the build; 0 uses configured limits, not literally unlimited parallelism. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `DATA_COMPRESSION index option` | Can select NONE, ROW, PAGE, COLUMNSTORE, or COLUMNSTORE_ARCHIVE where supported by the index type and version. ROW/PAGE apply to rowstore; columnstore modes apply to columnstore and archive trades access CPU for storage. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `XML_COMPRESSION index option` | SQL Server 2022+ option for eligible indexes containing XML data, compressing XML binary large object storage. It has CPU/storage tradeoffs and can be set at partition scope. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/xml/xml-indexes-sql-server?view=sql-server-ver17)) |
| `ON PARTITIONS compression option` | Scopes DATA_COMPRESSION or XML_COMPRESSION choices to selected partitions of a partitioned index. It is invalid for a nonpartitioned index and can leave partitions with different compression states. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `FILESTREAM_ON index option` | Places FILESTREAM data for an applicable clustered index operation on a filegroup or partition scheme. It is not a general location option for every index or platform. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `WAIT_AT_LOW_PRIORITY` | Controls how an online index operation waits for a schema-modification lock, including duration and blocker-handling choices. Low priority reduces blocking risk but can still time out, self-abort, or terminate blockers depending on settings. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/guidelines-for-online-index-operations?view=sql-server-ver17)) |
| `ALTER INDEX PAUSE` | Pauses a supported resumable index operation. The in-progress structure and resources remain, and writes/DDL can have restrictions while it is paused. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/guidelines-for-online-index-operations?view=sql-server-ver17)) |
| `ALTER INDEX RESUME` | Continues a paused supported resumable index operation. Resume options and original definition constraints apply; inspect current operation metadata first. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/guidelines-for-online-index-operations?view=sql-server-ver17)) |
| `ALTER INDEX ABORT` | Cancels a supported resumable index operation and discards its in-progress work; an aborted operation cannot be resumed. ([source](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/guidelines-for-online-index-operations?view=sql-server-ver17)) |
| `Maximum 32 rowstore key columns` | A relational index key can contain at most 32 columns. Key column count differs from INCLUDE column count; avoid solving a wide projection by moving every output into the key. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Clustered and nonclustered key byte limits` | Current SQL Server allows up to 900 bytes for clustered keys and 1,700 for nonclustered keys, subject to data types and actual value widths. Earlier versions had different limits; oversized existing varchar values can make later writes fail. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Maximum 999 nonclustered indexes per table` | SQL Server supports up to 999 nonclustered indexes per table (including PK/UNIQUE backing indexes, excluding XML indexes). This is a platform ceiling, not a sensible design target. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |
| `Index key type restrictions` | Some large-object types cannot be index key columns, though certain types can be included. Data-type, computed-column, and version rules vary by index type; check the operation-specific CREATE INDEX documentation. ([source](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)) |

# Cross-item comparison

Clustered versus nonclustered is about where table rows live; heap versus clustered is the table storage choice. Key columns establish order, included columns provide leaf coverage, and RID/key lookups fetch base rows. A seek, scan, or lookup must be judged by qualifying row count and actual cost.

# Examples

Use the examples in the overview and concepts with your own representative query and data distribution. A DDL statement creating an index proves only that the structure exists; compare actual row counts, reads, writes, and plan alternatives before retaining it.

# Common mistakes

- Adding every suggested missing index independently.
- Treating key order as irrelevant or placing all columns in INCLUDE.
- Dropping an index because counters are zero shortly after restart.
- Rebuilding every index on an arbitrary schedule.
- Assuming online means no locks or resource impact.
- Applying rowstore fragmentation advice to columnstore or memory-optimized indexes.
- Treating SQL Server 2025 vector preview as a stable cross-platform feature.

# Knowledge checks with answers

1. **What is the first experiment before adding a key?** Measure representative query shape, selectivity, reads, writes, and actual estimates.
2. **How do you distinguish rowstore from columnstore?** Rowstore B+ tree entries are row-oriented; columnstore stores compressed per-column segments grouped into rowgroups.
3. **What does a filtered index save?** It can avoid storing rows outside its predicate, reducing size and maintenance if queries imply the filter.
4. **What does rebuild do to index stats?** Recreating the index refreshes its statistics as a side effect.
5. **What does the usage DMV miss?** Full lifetime history and some specialized index types, including spatial and memory-optimized usage.
