# sweep-line events and active intervals — Reference: Invariants, complexity, and limits

## Scope and version

This reference provides a checklist for proving and analyzing a sweep, from one-dimensional events to geometric active structures.

## How this group fits the mental model

The invariant connects processed events to the summary used for the answer. Cost analysis then separates sorting, event scanning, and active-structure work.

## Supplied names explained

- **Sweep-state invariant:** exactly which intervals or objects are represented immediately before or after a coordinate's events.
- **Event conservation:** each valid start is balanced by its end; after all events the active count returns to zero when every interval has ended.
- **Sort plus scan complexity:** typically O(n log n) sorting plus O(n) event traversal.
- **Active structure update cost:** include each heap/tree/set update; it may contribute O(log n) per event.
- **Duplicate event handling:** aggregate identical-coordinate deltas or process them with an explicit semantic tie rule.
- **Large coordinate ranges:** avoid memory proportional to the largest raw coordinate unless constraints make that safe.
- **Insufficient aggregate state:** a count cannot answer identity, maximum height, or arbitrary covered length without more structure.
- **Endpoint off-by-one cases:** test touching, zero-length if permitted, equal endpoints, and point queries exactly at start/end.

## Cross-item comparison

An event counter is simple and fast for peak concurrency. A heap adds ordering to release the earliest end. A segment tree maintains a richer interval summary but has more invariants and implementation risk. Choose the least state that can answer the query, not the least state that happens to pass examples.

## Examples

For two half-open intervals `[1,3)` and `[3,5)`, the active count after processing both events at 3 is one, not two. For an inclusive flower interval `[3,3]`, a query at 3 must count it; the comparison is `start<=t && t<=end`. These are different semantics even though both involve equal endpoints.

## Common mistakes

- Proving the sorted event sequence but not the state invariant.
- Omitting active-structure costs from complexity.
- Reporting a temporary count generated by arbitrary same-coordinate event order.
- Forgetting event conservation, revealing a missing or duplicated end event.
- Confusing online insertion with offline sorting; some calendar problems receive bookings one at a time.

## Knowledge checks with answers

1. **What is a useful final conservation check?** Active count returns to zero after all valid start/end events.
2. **What are the usual complexity components?** Event generation, sorting, scan, and each active-structure update/query.
3. **Why does `activeCount` fail for skyline?** It cannot determine the maximum active height.
