# architecture patterns multi-region tenancy and reliability — Reference: SLSA provenance

Sources: [SLSA v1.2 specification](https://slsa.dev/spec/v1.2/), [Build provenance](https://slsa.dev/spec/v1.2/build-provenance), [Build requirements](https://slsa.dev/spec/v1.2/build-requirements), [Build levels](https://slsa.dev/spec/v1.2/build-track-basics), [Source requirements](https://slsa.dev/spec/v1.2/source-requirements), [verification guidance](https://slsa.dev/spec/v1.2/verifying-artifacts), [FAQ](https://slsa.dev/spec/v1.2/faq), [in-toto attestation framework](https://github.com/in-toto/attestation).

## Scope and version

This lesson describes approved SLSA (Supply-chain Levels for Software Artifacts) v1.2, available on 2026-11-20. It has distinct Source and Build tracks. Say “SLSA Build L2 (v1.2)” rather than the ambiguous “SLSA 2.” The v1.2 Build track defines L0 through L3; the Source track has its own levels. Do not apply the older single-track SLSA 1–4 model to v1.2.

SLSA is a framework of requirements, not a scanner, certificate, product, or guarantee that code is benign. Provenance is an attestation; a verifier must validate it against a trust and release policy.

## How this group fits the mental model

A release is the result of source revision, dependencies, build definition, build platform, execution, artifact storage, and deployment. Attackers can alter source, steal builder credentials, change inputs, compromise a worker, replace output after build, or publish malicious but correctly built code. SLSA asks what confidence a consumer can place in source history and build provenance.

The useful question is not “Is there an attestation?” It is: “Does it identify these exact bytes, come from a builder we trust for this repository and workflow, describe expected inputs, and meet the level required by our policy?”

## Supplied names explained

- **SLSA provenance** is verifiable information about where, when, and how artifacts were produced. The SLSA Build Provenance predicate is carried in an in-toto Statement. Its `subject` identifies outputs by digest. Its `predicate` contains a `buildDefinition` (build type, parameters, resolved dependencies) and `runDetails` (builder identity and execution information). The producer authenticates the attestation; the consumer validates both its cryptographic envelope and policy-relevant claims.

### Build track levels

- **Build L0:** no SLSA Build requirements.
- **Build L1:** provenance exists and identifies outputs by cryptographic digest while describing the build. This improves traceability; it does not by itself provide strong resistance to a malicious or compromised build environment.
- **Build L2:** signed provenance is generated by a hosted build platform. The intent includes making post-build artifact tampering harder to conceal. The verifier must still trust and constrain the platform and the identity/workflow producing the statement.
- **Build L3:** a hardened build platform provides stronger isolation and protection against tampering during the build. It does not certify the source as safe or make dependencies trustworthy.

Levels bundle minimum requirements, not a universal security score. Requirements and names are track- and version-specific; cite the exact version in policy and audit records.

### Source track

The Source track covers properties of how a source revision was created and controlled. It does not prove how a binary was built. A project can have strong source controls but an untrusted builder, or a hardened builder compiling malicious source. Evaluate Source and Build evidence together when both questions matter.

### What provenance says—and does not say

- `subject`: output artifact and digest; compare this with the exact bytes being installed.
- `buildDefinition.buildType`: build template; its specification should define how to interpret the build.
- `externalParameters`: inputs controlled from outside the builder; verify the parameters relevant to policy and reject unexpected ones where appropriate.
- `resolvedDependencies`: build-time dependencies. Pin them to immutable digests/revisions where possible. Completeness depends on the level and implementation; hidden network fetches weaken policy checks and reproducibility.
- `runDetails.builder.id`: builder identity. Consumers need explicit trust rules for builder IDs, repositories, workflows, and release identities.

Provenance does not prove source review, reproducibility, absence of vulnerabilities, benign intent, or that the producer is honest. SLSA identifies code quality, producer trust, and transitive dependency trust as areas outside an artifact’s individual level. Evaluate dependencies separately where policy requires it; a parent’s level does not transfer to its dependencies.

## Consumer verification procedure

1. Obtain the artifact and attestation through an authenticated channel; adjacency is not trust.
2. Verify signature/envelope, certificate or key chain, trusted roots, and required transparency evidence.
3. Parse a supported attestation type and version. Reject malformed, ambiguous, or unknown formats instead of guessing.
4. Match the subject digest to the exact artifact. A tag or filename is mutable and cannot substitute for a digest.
5. Evaluate builder identity and claims against policy: repository, workflow/build type, source revision, invocation parameters, dependency set, and required track/version/level.
6. Fail closed for release admission when required evidence is missing or the decision is indeterminate. Record the decision and evidence.
7. Run vulnerability, malware, license, and code-quality checks separately; provenance complements them.

A valid signature proves integrity and signer identity relative to keys and policy. It does not make the statement true if the signer or builder is compromised. Trust in the platform is part of the security argument.

## Example: .NET API and React release

CI builds a .NET API image and React static bundle. Pin build actions and tools to immutable revisions where feasible, lock dependencies, minimize credentials exposed to build steps, separate untrusted pull-request builds from release signing, and use isolated ephemeral workers. Emit provenance for each artifact, each bound to its own digest and source revision.

At deployment, policy checks the API image digest against the approved release workflow and protected repository ref. The frontend needs its own provenance; evidence for the API does not cover it. A release manifest can bind both digests into one release. Rebuilding changes the artifact digest and therefore requires new evidence. Pinned dependencies constrain inputs but do not prove them safe.

## Design choices and incident response

- **Hosted vs self-hosted builder:** hosted platforms may simplify authenticated provenance and isolation; self-hosting provides control but makes the organization responsible for control plane, workers, signing identities, and evidence generation.
- **Reproducibility vs provenance:** independent output comparison can detect differences; provenance records the asserted build process. Neither replaces the other.
- **Attestation transport:** registries, release bundles, or separate stores can carry evidence; preserve digest binding when mirroring artifacts.
- **Level target:** choose from threat model and actual platform guarantees. A workflow that emits provenance is not automatically L3; check each normative requirement and trusted system boundary.
- **Incident response:** preserve artifacts, attestations, builder logs, workflow definitions, dependencies, signing events, and identity audit logs. Revoke compromised credentials, rebuild on trusted infrastructure, find all consumers of affected digests, and do not infer that an old valid signature remains acceptable.

## Cross-item comparison

- **SBOM** describes components believed present; **provenance** describes how an artifact was produced. Bind both to the artifact digest.
- **Signature** verifies integrity relative to a key/identity; **provenance** carries build claims; **transparency log** makes events auditable. They are complementary.
- **Build track** concerns production of packages; **Source track** concerns source revision creation and control.
- **Reproducible builds** compare outputs independently; provenance explains a claimed process. A reproducible malicious build is still malicious.

## Common mistakes

- Saying “SLSA 3” without track and version.
- Checking only for an attestation rather than verifying signature, exact subject digest, builder, and relevant parameters.
- Trusting any build because it ran on a hosted CI product; workflow permissions and identity still matter.
- Assuming SLSA proves the code is safe, reviewed, vulnerability-free, or that dependencies have the same level.
- Signing after untrusted steps can alter output, or exposing a broad long-lived signing key to every build.
- Treating provenance as an SBOM, or using a mutable tag as artifact identity.

## Knowledge checks with answers

1. **Does Build L3 mean the artifact is safe?** No. It raises confidence in specified build properties; it does not establish code quality, benign intent, or absence of vulnerabilities.
2. **Does provenance authorize deployment if its digest differs from the deployed image?** No. The subject must match the exact bytes.
3. **Does a dependency inherit the parent’s SLSA level?** No. Assess its own evidence if policy requires it.
4. **What is the distinction between Build and Source?** Build describes how the package was produced; Source describes how the source revision was created and controlled.
5. **What should a verifier do with an unknown builder or unexpected parameter?** Apply explicit policy and reject/quarantine when the required trust cannot be established; a valid signature alone does not mean approval.

## Examples

The API image and frontend bundle are built as separate outputs. Each provenance statement binds its own output digest to the same protected source revision but records the relevant build type and resolved dependencies. The deployment verifies both digests independently; an API attestation cannot authorize a changed frontend bundle.
